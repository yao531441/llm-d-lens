## DisaggregatedSet 审核计划

DS、资源预算及推断等设备预算的基线配置必须先准备计划，再明确确认摘要。准备过程不会创建 Run 或 Kubernetes 资源。
计划绑定所有者和集群，保存最终工作负载 YAML、命名空间、Router values 及校验过的本地 Chart 包；
消耗计划与创建 Run 在同一事务中完成。重复成功确认返回原 Run。修改配置、运行参数或集群
必须重新准备；仅更新同一集群的会话不改变计划身份。

| `POST /api/v1/deployments/runs` | 在原始请求上增加 `prepared_plan_id`、`expected_plan_digest`、`acknowledge_unknown`。重新预检；绑定变化、约束失败或未确认未知项返回 409。 |

准备后保留原始部署请求，仅添加以下字段：

```json
{
  "prepared_plan_id": "准备接口返回的 ID",
  "expected_plan_digest": "sha256:准备接口返回的摘要",
  "acknowledge_unknown": true
}
```

每个审核用例包含 `manifest`、`namespaceManifest`、`manifestChecksum`、`namespace`、
`routerManifest`、`routerValues`、`chartChecksum`、辅助 `resources` 和 `sourceCommit`。`preflight.status`
为 `pass`、`fail` 或 `unknown`。找到模型内的放置方案并不等于资源预留：准入、配额、
并发调度、滚动升级额外资源和未建模约束仍为未知。确认未知风险不会覆盖失败约束。
放置策略使用拓扑键时，`preflight.assignments` 条目包含 `domain`。`preflight.slicePreview` 为每个
DisaggregatedSet 用例给出 `caseIndex`、`workload`、`slices`、`maxFeasibleSlices`（按该用例策略基于空闲资源
的估算，未知时为 `null`）、`placementPolicy`、`sliceRouting`（冻结的 Router values 包含亲和评分器时为
`prefer`）、`roles`、`sliceRequests`、`acceleratorResources` 和 `placement`（每 Slice 的模拟 Pod 放置，含节点和域）。

`storageResources` 包含已审核的附属 PV/PVC 清单；存储定义变化或已有 PV 同名冲突会被拒绝。
`secretReference` 标识凭据来源，不含凭据字节，也不冻结凭据轮换。准备阶段拒绝将 dynamic-pvc
镜像到新的部署命名空间。

用例还包含可选的 `comparisonBudget`。既有用例重试接口
对审核部署返回同样的审核响应，拒绝内联模型令牌，需轮换已配置的 Secret 来源。将返回的
`request` 加上新计划 ID/摘要提交到 `POST /runs`；旧资源保持不变。
主动探测还返回 `captureErrors`、`after` 和包含不可覆盖报告校验和的 `artifact` 清单；
被动读取在存在历史探测时返回 `lastProbe`。
verify 请求还接受 `metrics_only`（与 `smoke` 互斥）：不发送任何推理请求、不持久化报告，
仅读取各 Pod 当前模型服务指标计数，返回按 Pod 名组织的 `metrics` 和 `metricsCollectedAt`。
计数值是采集时刻的快照，不是速率。

<TabItem value="python" label="Python API">

`llm_d_lens.deploy.prepared_plans` 提供 `prepare(manager, request, owner_user_id=...)`、
`public_plan(plan)` 和 `consume(manager, request, owner_user_id=...)`。内部调用者必须先完成
动作权限与集群访问检查。

```python
from llm_d_lens.deploy.contracts import DeploymentRunCreateRequest
from llm_d_lens.deploy.prepared_plans import prepare, public_plan, consume

async def prepare_for_review(manager, request_body, owner_user_id):
  request = DeploymentRunCreateRequest.model_validate(request_body)
  plan = await prepare(manager, request, owner_user_id=owner_user_id)
  return public_plan(plan)

async def execute_reviewed(manager, original_body, reviewed_plan, owner_user_id):
  request = DeploymentRunCreateRequest.model_validate({
    **original_body,
    "prepared_plan_id": reviewed_plan["id"],
    "expected_plan_digest": reviewed_plan["digest"],
    "acknowledge_unknown": True,
  })
  return await consume(manager, request, owner_user_id=owner_user_id)
```

带认证上下文的路由函数也支持准备重试与验证：

```python
from llm_d_lens.deploy.router import (
  prepare_execution_restart, verify_deployment_execution, RuntimeVerificationRequest,
)

async def review_restart(execution_id, authenticated_request):
  return await prepare_execution_restart(execution_id, authenticated_request)

async def probe_execution(execution_id, authenticated_request):
  return await verify_deployment_execution(
    execution_id, RuntimeVerificationRequest(smoke=True), authenticated_request,
  )
```

验证反映实际所有权和节点拓扑，不认证物理互连。HTTP 成功或聚合指标增量不能证明单个请求
的 P/D 路由与 KV 传输；没有关联证据时，这些维度保持未知。冻结执行跳过 Helm CRD 安装和
hooks，兼容控制器与 CRD 需单独安装。审核仅接受已分类的命名空间级资源，拒绝嵌入的 Secret
对象（包括嵌套 List）及其他命名空间。命名空间所有权标记防止清理已有或被替换的命名空间。
计划唯一单独生成的集群级资源是经过审核的存储附属 PV；不接受任意集群级 YAML。

对于已注入探针的 vLLM 0.26.0 NIXL pull worker，通过判定要求：响应与 decode 请求唯一对应、
远端 prefill 请求身份明确、全部 TP rank 的非空接收完成及发送端确认、Pod/引擎身份稳定、
DS 所有权与 revision 匹配，且未观察到失败后重算。证据记录实际 Pod UID、同 Slice/域情况
及块数。跨 Slice 是可观测结果，不违反软路由偏好。其他版本/连接器、缺失 rank、只有全缓存
命中通知而没有传输，或采集不完整时保持未知。判定仅覆盖本次有界探测请求。

### Guide 配置输入

仅供 UI 使用的 `POST /api/guide-planning/prepare` 接收 `guide`、`accelerator`、`modelServer`，
返回 `ready`、完整 `commit` 和 `capabilities.disaggregatedSet`。
对带可选 `clusterId` 和 `model` 的 DS 来源，`recommendation` 包含 `guideDefault`（`slices`、`placementPolicy`）、
`capacity`（`sliceRequests`、`acceleratorResources`、`podsPerSlice`、`maxSlices.None`、`schedulableNodes`，以及
含各域 `domainDetails`、`feasibleDomains`、`exclusiveTopologyDomains` 的 `topologyKeys`，以及 `unmodeled`：
Slice Pod 通过 ResourceClaim 申请加速器而估算未计入时列出 `DRA`）、建议的 `placementPolicy`
及其 `maxSlices` 和 `reasons`，以及该集群上同模型近期成功 Evaluation 用例的 `history`（`slices`、P/D 形态、
`accelerators`、`maximumStableQps`、`throughputTps`、`accelerator`、`guideCommit`、`slaTargets`、`workloadLabel`，以及按请求形态和
SLO 目标分组、与速率阶段无关的 `evidenceKey`）。它从不选定 Slice 数；容量按
Guide 默认角色估算，不是预留。
`POST /api/guide-planning/plan` 还接受官方源的 `expectedSourceCommit` 及 `disaggregatedSet`：

```json
{"disaggregatedSet":{"slices":2,"placementPolicy":{"type":"ExclusiveSlice","topology":"topology.kubernetes.io/zone"},"sliceRouting":"prefer"}}
```

规划返回 `disaggregatedSet` 和含展开 Pod 数与资源请求的 `workloadSummary`。带集群会话的 DS 规划还返回
`sliceCapacity`（与 `recommendation.capacity` 结构相同，按渲染后的角色计算；无法读取清单时为 `null`）。角色副本数是
**每 Slice 的数量**；group size 展开 leader/worker Pod，需求由资源请求而非 TP 值计算。
合法多 Slice 不会被改写为 1；多 Slice 与 External 扩缩容组合被拒绝。`sliceRouting`
为 `inherit` 或 `prefer`；后者要求受支持的 llm-d Router 1.0 单 EPP profile，添加 prefill
软亲和评分器，不保证严格同 Slice 路由。官方和远程自定义源从固定 Git 快照渲染；外部
Kustomize 依赖必须纳入源码。本地输入及引用文件先复制再渲染，来源标记
`revisionKind="content-snapshot"`、`snapshotChecksum`（SHA-256），`commit` 为该哈希前 40 位，
不是脏工作树的 Git HEAD。
`POST /api/v1/configurations/render` 接收 `candidate_config.disaggregated_set`，
保存为 `content.disaggregatedSet`。`workloadSummary` 还包含用于自定义来源能力识别的
`disaggregatedSet` 布尔值。Python 使用 `llm_d_lens.configuration.models` 的
`CandidateConfig`/`GuideSource`，以及 `llm_d_lens.configuration.service` 的
`render_configuration(RenderRequest.model_validate(request_body))`，字段和验证规则相同。

Python 路由函数是 `llm_d_lens.deploy.guide_planning.prepare(request)` 和 `plan(request)`，
参数为携带 JSON 请求体和既有集群/会话上下文的 Starlette `Request`；这些 UI 专用接口建议
通过浏览器流程使用。

在为部署规划指定操作者偏好时，请使用英文，例如
`prefer prefix cache`（偏好前缀缓存）、`more GPU for performance`（更多 GPU 以提升性能）
或 `use fewer GPU resources`（使用更少的 GPU 资源）。确定性规划器只匹配英文偏好关键词；
不再支持中文关键词别名。

## Python 领域契约

### Manual / Agentic 共享规划

新的创建界面在两种决策模式下都使用现有 Agentic 运行生命周期。
不携带 `requirements` 的旧请求保留兼容行为。

<Tabs>
<TabItem value="rest-api" label="REST API">

**`POST /api/agentic-deployments`** 返回 `201` 和 `AgenticDeploymentRun`。
浏览器使用的 `/stream` 通过 SSE 返回进度及相同的完成结果。两者都不会部署资源。

除了 Standard 服务参数和有效会话字段，还支持：

- `planning_mode`：`manual` 或默认的 `agentic`。Manual 是基于规则的规划器，不初始化外部 AI 规划器。
  Agentic 需要可用的 AI 提供方（`ai_provider_id` 或服务端环境配置的提供方），否则返回 `422`；
  AI 候选生成或排序失败时请求直接失败，不回退到规则。
- `requirements`：模型、集群、目标、`hard_constraints.maxAccelerators`、
  负载、性能目标、必须 / 禁止机制 ID 和未知字段。
  保留原机制 ID `pd_disaggregation`、`prefix_routing`、`external_kv_cache`、
  `prefix_cache` 和 `chunked_prefill`。源码组合还支持目录中的 `index`（精确路由）、
  `load-routing`、`wide-ep` 和 `speculation` 等机制，必须由最终资源验证，而非仅记录用户意图。
  `affinity` 与 `index` 是不同机制。目标默认 `balanced`，
  仍支持 latency、throughput、cost、reliability；缺失负载字段保持未知。
- `requirements.hard_constraints.providerRef`：可选的显式部署方式，支持
  `optimized-baseline`、`pd-disaggregation`、`precise-prefix-cache-routing` 和
  `tiered-prefix-cache`。其他方式被拒绝；规划、修订及审批会排除不匹配的候选。
- `requirements.workload.p95InputTokens`：可选正数，表示输入长度的 P95，
  与平均值 `inputTokens` 独立；省略时保持未知。
- `requirements.performance_targets.e2eMs`：可选正整数，表示端到端 P95 延迟目标，
  单位毫秒，与 `ttftMs` 和 `tpotMs` 并列。测试排名要求每次完整重复均满足所设目标。
- `planner_prompt`：可选 AI 目标。显式选择 `ai_provider_id` 后，可以从任意语言的明确陈述中
  补充未知的 `prefixReuse` 和 `prefillHeavy`，结构化值优先。
  补充后设置 `workload.interpretationSource=ai_goal`；解析失败返回 `422`。
  数值限制不会自动推测。Manual 不调用外部 AI 提供方。
- `planning_facts.max_candidates`：Agentic 保留候选数量上限，1–10。
  Manual 即使收到较小上限，也保留各个不同的已支持能力族。
  实际空闲资源优先于客户端提交的硬件数据。
- `execution_policy.max_total_duration_minutes`：规划截止时间，1–180 分钟。
- `execution_policy.allow_trials`：默认 false；启用后允许另行审批 `/optimize`，
  不会在规划期间自动开始测试。

```json
{
  "model": "Qwen/Qwen3-8B",
  "deployment_name": "reviewed-model",
  "cluster_session_id": "00000000-0000-0000-0000-000000000001",
  "storage_type": "model-cache",
  "storage_volume_id": "registered-cache-id",
  "replicas": 1,
  "tensor_parallel_size": 1,
  "planning_mode": "manual",
  "planning_facts": {
    "model_weight_gib": 16,
    "vram_per_gpu_gib": 1,
    "free_gpu_count": 0,
    "max_candidates": 3
  },
  "requirements": {
    "model": "Qwen/Qwen3-8B",
    "cluster_id": "registered-cluster-id",
    "objective": "throughput",
    "hard_constraints": {"maxAccelerators": 4},
    "workload": {"prefixReuse": null, "prefillHeavy": null},
    "performance_targets": {"ttftMs": null, "tpotMs": null},
    "required_features": [],
    "forbidden_features": ["external_kv_cache"]
  },
  "execution_policy": {"mode": "approval_required", "allow_trials": false}
}
```

将示例 ID 替换为有效会话、对应集群和就绪模型缓存。身份不匹配、不支持的约束、
必须机制不受支持或资源上限不可行时返回 `422`；负载未知本身不会排除技术兼容候选。

响应增加 `configuration_plan`、`revision` 和可选 `parent_run_id`。
共享方案保留需求、机制决策、资源估算、准确的可部署 `configuration`，
以及分别列出的已检查 / 待检查项。`planning_checked` 不代表资源清单、准入或性能已通过。

`configuration_plan.optimization_choices` 列出五个可勾选优化
（`prefix_routing`、`prefix_cache`、`chunked_prefill`、`external_kv_cache`、
`pd_disaggregation`），包含 `checked`（出现在 `forbidden_features` 中时为 false）、`auto`、
`intended` 和 `reason`。已勾选但最终决策未启用的优化即为降级。至少有两个可用加速器时 P/D 默认开启。
Manual 收到平均 `inputTokens` 和 `outputTokens` 时，比较 AIC 对 P/D 与合并服务的最佳预测（先看是否满足
`ttftMs`/`tpotMs`，再看吞吐），并将结果写入 `requirements.workload.aicPrefillDecode` 和
`aicPrefillDecodeReason`；没有 AIC 结果时 P/D 保持开启。Manual 还会根据同一拓扑的 AIC 预测设置每个候选的
`slo_status`，先按 SLA 状态、再按 P/D 决策、再按勾选的优化排序；不满足 SLA 的候选排在最后而不是报错，
且不会选择 `precise-prefix-cache-routing`。提供负载目标时，两种模式在 AIC 支持当前模型与硬件时都用 AIC 确定拓扑规模。

**`POST /api/agentic-deployments/optimizations/preview`** 根据 `requirements` 请求体和可选的
调用方上报 `available_accelerators` 返回相同的 `optimization_choices`。该接口为纯计算，
不访问集群，需要 `deployment:agentic:read` 权限。

两种模式携带结构化需求时，都会展开原生 CPU KV 缓存与基线、精确路由和 P/D 的适配组合。
独立分层缓存通过 `guideSettings.cacheCpuGiB` 设置容量，组合通过
`guideComposition.nativeCpuCacheGiB` 设置容量。每个服务副本最多 8 GiB，
缓存总量不超过已观察空闲主机内存的 25%；内存未知时不自动分配缓存。
`resource_estimate.cpu_cache_gib` 记录合计容量。计划缓存决策在源码绑定渲染成功前保持
`unknown`。Manual 存在模型 / 显存并发容量估算时，序列数受其约束。

候选的可空布尔字段 `prefix_routing` 独立控制前缀亲和路由：
`true` 将源码声明的亲和插件组合到 default/prefill 调度配置，`false` 移除亲和但保留负载路由，
`null` 保留旧提供方行为。生成配置携带 `prefixRouting`，共享 Guide 渲染器也消费此选项。
部署包保留 `router-prefix-source.yaml`，校验最终参数与源码一致，并保留 P/D 处理器和 decode 调度配置。

Manual 即使设置了并发目标也始终枚举全部已注册提供方拓扑；AIC 负载目标推荐仅用于 Agentic。
Manual 先排除已知不满足 SLO 的候选，再依次比较机制覆盖、副本能否承载并发目标和偏好：吞吐优先 P/D，其次前缀路由；
低延迟优先前缀路由；成本优先较少加速器；可靠性优先多个服务副本。
默认 `balanced` 及最终平局均优先较少加速器。保留候选优先覆盖不同方案 / 缓存组合。
保留候选也覆盖独立路由选择。选择说明公开此规则，而不宣称实测最优。
缓存与路由组合不继承未组合拓扑的性能证据。

#### 全量 Guide 源码组合

集成编辑器使用所选集群固定版本的源码，而不是五个写死的优化开关：

- **`GET /api/guide-planning/source-catalog?clusterId=...`** 返回 `commit`、
  `guides`、可选 `assets`、源码参数和 `optimizations.items`。目录包含共享机制定义及额外发现的
  Guide；出现在目录中不代表已兼容或已有可执行适配器。
  `environment` 保留 `guides/env.sh` 中的字面量直接赋值和 `${VAR:-default}` 字面量默认值，
  包括固定的 Chart 版本；不会执行 Shell 命令或动态表达式。
- **`POST /api/guide-planning/source-preview`** 接收 `clusterId`、`commit` 和
  `unit`（包含目录 `path` 和可选的类型化修改），返回渲染后的资源及观察到的优化标志。
- **`POST /api/guide-planning/compose`** 接收固定的 `commit`、`clusterId`、
  `clusterSessionId`、`namespace`、`modelCacheEntryId`、`units`（1–60 项），以及可选
  `router`、`guideSelection`、`deploymentIntent`、`finalConfiguration`。
  `finalConfiguration` 使用前一版本的 `baseChecksum` 绑定编辑后的 YAML。
  返回 `files`（`deployment.yaml`、`provenance.json`）、有效 `optimizations`、
  `compositionChecksum` 和分别记录的资源 / 准入校验。可选 `validateCluster` 仅执行服务端准入试运行，
  不会部署。
  DRA 大小调整支持生成的 `ResourceClaimTemplate` 及其 `ExactCount` 请求。
  设备数量按各角色的张量并行度、副本数及自动扩缩容上限计算，非加速器请求保持不变；
  可用数量使用匹配集群硬件配置的可用设备清单。外部 Claim、含糊的分配方式及混合硬件配置
  下无法区分的可用数量会被拒绝；设备选择器、网卡及放置仍需准入和运行时验证。
  自动硬 P/D slice 放置会为能容纳完整 slice 的域添加强制节点亲和性，域列表位于
  `sliceLayout.recommended.eligibleDomains`。保留已有亲和性，不替换显式 slice 策略；
  此检查不预留设备，可用容量变化后应重新生成方案。
- **`POST /api/agentic-deployments/{run_id}/composition`** 将组合结果保存到空闲部署方案。
  提交当前 `revision`、`compare` 和 `candidates`；每项包含 `candidate_id`、
  用于恢复编辑器的 `draft` 和 `composition` 组合输入，也可携带明确的 `error`。
  `compare=true` 必须覆盖全部保留候选。Manual 在通过校验的候选中选择最终清单覆盖最多的方案；
  Agentic 保留有效的已选推荐，否则明确报告已验证的替代方案。

成功组合后递增 `revision`，使旧审批和性能证据失效，并在 `configuration_plan` 中保存
`source_bundle`、`source_draft`、`source_request`、`source_candidates` 和可选 Service
`endpoints`。`configuration.checksum` 是生成部署 YAML 的审核令牌。
优化决策同时携带 `catalog_id` 和兼容旧接口的 `capability_id`。

源码接口要求 `guide:plan:execute` 和对应集群访问权限；方案组合另要求
`deployment:agentic:create`。模型缓存和存储读取保留现有权限检查，不执行 Guide shell 脚本。
过期源码 / 编辑版本返回 `409`，无效组合输入返回 `400`；方案比较失败返回 `409` 且不替换旧方案，
方案组合超时返回 `504`。

审批还要求 `endpoint`，必须是已审核 `configuration_plan.endpoints` 中的精确值：

```json
{
  "configuration_checksum": "sha256:reviewed-deployment-yaml-checksum",
  "endpoint": "reviewed-inference-service:8000"
}
```

审批重新检查缓存绑定、可用设备、内存和必须 / 禁止机制，然后复用现有受管部署生命周期。
源码快照使用 `runtime.modelSource=cached-readonly`，普通 `auto-cache` 行为不变。
多节点模型角色及尚无受管生命周期的集群级资源创建仍会明确阻止，不会部分部署。
唯一受限例外是 Router 认证 RBAC：ClusterRole 只允许创建 TokenReview 和 SubjectAccessReview，
并绑定到生成的 EPP ServiceAccount。运行时名称按部署隔离，创建时绑定命名空间 UID 所有权，
不会覆盖其他所有者或已被修改的对象。清理命名空间会通过垃圾回收删除这些精确资源并等待完成；
回收未完成会报告清理失败。其他集群级授权仍被阻止。
停止源码部署时，会先移除其 HPA/KEDA 自动扩缩容资源，再将模型控制器缩容到零；
重新部署已审核快照时会恢复这些自动扩缩容资源。
源码方案的 `/optimize` 还需提供以候选 ID 为键的 `endpoints`，测试使用已审核的源码候选资源，
不会换成基础模板。

**旧版 `POST /api/agentic-deployments/{run_id}/select`** 返回 `200`：

- `{"candidate_id":"..."}` 选择已有合法候选。
  对源码方案，这会恢复该候选已审核的精确资源和编辑参数、递增修订号并清除端点选择，
  同时保留已完成的试验结果。未审核的候选及尚未结束的试验会阻止切换。
  源码方案的参数修改和生成必须使用 `/composition`；旧版编辑字段不能覆盖已审核的源码快照。
- `{"candidate_id":"...","role":"decode","replicas":2}` 创建实时校验后的用户修订。
  `role` 为 `decode` 或 `prefill`；可选 `tensor_parallel_size` 和 `replicas` 范围为 1–128。
  运行参数支持 `max_model_len`（256–1048576）、`gpu_memory_utilization`（0.5–0.98）、
  `max_num_seqs`（1–4096）和 `max_num_batched_tokens`（256–131072），作用于所有服务角色。
- `{"candidate_id":"...","native_cpu_cache_gib":4}` 修改已选 CPU KV 缓存的每模型副本 GiB 容量，
  大于零且不超过 1024；总量必须在当前发现的空闲主机内存的 25% 内。
- `{"candidate_id":"...","render_resources":true}` 通过与 Configuration 相同的渲染器生成固定源码版本的
  YAML 并检查一致性。会读取集群 / 存储并可能获取官方源码，但不会安装资源。不能与修改同时提交。

修改保留原运行，设置 `parent_run_id`、递增 `revision`，并使旧资源检查和性能证据失效。
失败的编辑返回 `409`；渲染错误保留对应状态，并发改变的选中方案会被拒绝。
成功生成后设置 `validation.status=resources_checked`，清单位于
`configuration_plan.configuration.content.officialGuide.renderedManifest`。
旧渲染器仍兼容原来的五个机制 ID；更完整的目录约束必须使用 `/composition`。
Manual 保留不同已支持方案 / 缓存能力族并调用
`{"candidate_id":"...","render_resources":true,"compare_combinations":true}`。
此选项仅供 Manual 使用，检查保留候选的固定源码，不发布中间选择；
返回被排除候选，选择源码校验后实际启用能力覆盖最多的组合，覆盖相同才按规划顺序取舍。
`validation.coverage` 包含 `enabled`、`available_in_other_combinations` 和 `complete`。
缺少适配器标为 `unsupported` 而非 `conflict`；Agentic 未选择的可行方案可标为 `alternative`。
全部失败时返回 `409`，
保留原推荐并阻止审批。权限错误和意外服务错误直接传播，不作为方案不兼容处理。
不启用 `compare_combinations` 时，渲染保留用户显式选择的候选。
固定源码有效启用的前缀缓存和分块预填充即使继承自 Guide，
也记录为启用。Manual 对源码声明支持的运行参数自动启用，即使负载收益未知。
直接调用 vLLM 的源码未显式配置这些开关时，会添加使用选定镜像的强制 CLI 能力检查；
检查失败会阻止模型启动，不代表运行就绪或性能已经验证。
必须运行参数及显式禁用项在发布已检查配置前均需验证。
禁用引擎前缀缓存会排除依赖它的路由和卸载候选。
容量明确的 CPU 缓存方案所需前缀缓存记录为 `dependency`。
拓扑修订保留每副本缓存容量，显式缓存编辑可修改容量；两者均重新检查 25% 主机内存预算，
审批会再次刷新这一预算。
准入、就绪和负载性能仍待检查。

**`POST /api/agentic-deployments/{run_id}/approve`** 返回 `202`。
新的共享方案必须先生成并审阅资源，否则返回 `409`。
提交 `{"configuration_checksum":"<reviewed configuration checksum>"}`；
缺失或过期的校验和也返回 `409`。审批期间会拒绝重复审批及候选修改。
提交前会刷新资源容量。对 DisaggregatedSet 配置，首次审批返回 `configuration_plan.validation.preparedDeployment`，不会启动部署。
审阅其中的资源与预检结果后，再次提交相同的审批请求（源码组合需保留所选 `endpoint`），将 `prepared_plan_id` 设为返回的 `id`，`expected_plan_digest` 设为返回的 `digest`。
预检结果未知时须显式提交 `acknowledge_unknown: true`；预检失败不可执行。启动成功后返回 `deployment_run_id`。
生成成功不保证准入或就绪，旧审批行为保持兼容。

共享方案对旧的纯提示词 `/refine` 操作返回 `409`，应修改结构化需求并创建新计划。
已完成的新运行 / 修订可通过现有 `GET /api/agentic-deployments/{run_id}` 从快照恢复。

**`POST /api/v1/configurations/plan`** 保留为只检查意图的兼容接口，
不读取集群，不返回可执行候选、拓扑或已启用机制。
负载适用信号在真实规划前保持未知，不再伪造候选排名。

### 命令与不可变产物

| 契约 | 字段与约束 |
| --- | --- |
| `VersionedPayload` | 非空 `schema_version`；对象 `value` 默认为 `{}`；封装本身不规定生产方管理的字段。 |
| `ConfigurationArtifact` | `artifact_id` 默认为 UUID；`schema_version`、`kind`、`provider_ref`、`checksum` 非空；`media_type` 默认为 `application/yaml`；必须至少提供 `content` 或 `content_ref`。 |
| `DeploymentCreateRequest` | UUID `request_id`；`input_schema_version="v1"`；非空 `configuration_artifacts`；`deployment_policy` 默认为非 null 的 `VersionedPayload(schema_version="v1", value={})`；可选 `cluster_snapshot_ref`/`cluster_snapshot`；对象 `provenance`。 |
| `DeploymentKillRequest` | UUID `request_id`；`input_schema_version="v1"`；必填非空 `execution_id`；可选 `expected_namespace`/`reason`；对象 `provenance`。 |
| `DeploymentArtifact` | UUID `artifact_id`；非空 `artifact_hash` 和 `configuration_artifact_ids`；可选 `source_ref`、`manifest_ref`、`manifest_checksum`、`values_checksum`；必填 `rendered_payload`；`created_at`。 |

`provider_ref` 选择部署提供方，不转移配置所有权。当前
`GuideAdapterDeploymentService` 比通用 DTO 的限制更严格：每次 create 必须提供
**恰好一个包含内联 JSON 对象的产物**，且 `media_type="application/json"`。
运行规划器会将公开的运行请求拆分为 Case；不能直接向该适配器传入通用 YAML
或只有内容引用的产物并假定它支持。

`DeploymentExecution`；运行时绑定不改变配置所有权。

### RuntimeClass 发现与策略

`GET /api/v1/deployments/runtime-classes?cluster_id=CLUSTER_ID` 要求部署读取权限和目标
集群访问权限。可选的 `accelerator`、`access_mode` 用于查询已注册 profile 的建议值。
返回 `items`（`name`、`handler`、`scheduling`、`overhead`、`matching_nodes`）、
`profile_suggestion`、`available_suggestion`、`requirement="unknown"`、
`node_runtime_readiness="unknown"` 和 `warnings`。Kubernetes 连接或读取权限失败返回
HTTP 503，不会伪装成空列表；未知硬件或访问模式返回 422，Lens 授权失败返回 403。

在 `POST /api/v1/deployments/runs` 中指定 `runtime_binding.runtime_class`：

```json
{"runtime_binding": {"runtime_class": {"mode": "named", "name": "custom-runtime"}}}
```

Python 对应 `llm_d_lens.deploy.contracts` 中的
`RuntimeBinding(runtime_class=RuntimeClassPolicy(...))`。Standard 和 Agentic 创建请求
通过顶层 `runtime_class` 接受同一策略。

- `auto`：保留并校验清单已有的显式类；否则仅在目标集群提供 profile 访问模式建议的类时
  使用它，没有可用建议时省略 `runtimeClassName`。
- `node-default`：明确移除 `runtimeClassName`，使用节点默认运行时；此模式不依赖
  RuntimeClass 发现权限，也不验证设备注入是否可用。
- `named`：必须提供合法 DNS 子域格式的 `name`，并校验目标集群是否提供该类。
  类缺失或与 Pod 节点选择器、节点名称冲突时，在修改集群前失败。

省略运行时覆盖时沿用配置的 `provenance.runtime_class`，未保存偏好时默认 `auto`。
显式 `auto` 会覆盖已保存偏好。选择保存在部署 Case policy 中，供重试和恢复沿用。
五种模型 provider 共用部署适配器，生成新的部署产物，不改写原始 Configuration 或已有
执行；仅路由的 Pod 不受影响。离线渲染不再注入未经集群验证的 profile 默认类。
报告位于 `artifact.rendered_payload.value.deployment_contract.runtimeClass`。

类存在、节点选择器匹配，不代表必须使用该类，也不能证明各节点的 handler、CDI、驱动
或完整调度约束已就绪。不能仅凭 device-plugin 或 DRA 判断是否需要 RuntimeClass。
只有确认集群默认运行时已经提供设备访问时，才应选择节点默认模式。自动和指定名称模式
在部署时依赖可解析的显式目标集群；离线 provider 渲染不构成集群验证。

### 执行、观察与证据

普通 provider 渲染会把各角色的 `maxModelLen`、`maxNumSeqs`、
`gpuMemoryUtilization`、`blockSize` 和 `maxNumBatchedTokens` 映射为对应的 vLLM 参数。
P/D 分别使用 `prefill` 和 `decode`；其他 provider 使用 `decode`
（`precise-prefix-cache-routing` 也接受 `serving`）。角色未指定长度时，
使用 `model.maxModelLen`。显式整数控制项必须为正整数；
`gpuMemoryUtilization` 必须为有限数，且大于零、不超过一。
非法值会使验证或渲染失败，不会静默回退。匹配目标角色的 `customParameters`
覆盖结构化控制项。普通渲染会替换 `--name=value` 和 `--name value` 两种形式；
省略的字段保留 Guide 默认值。精确发布的 `officialGuide` 清单继续走现有清单验证路径，
不会由普通 provider 参数映射重写。

`DeploymentExecution` 包含 `execution_id`、`request_id`、`status`、`artifact`、
`configuration_artifacts`、可选 `endpoint`/`namespace`/`resource_snapshot`、
`provenance`、`evidence_refs`、可选版本化 `diagnostics` 和时间戳。
当前还包含 `forwarded_endpoint`、`monitoring_setup`（安装审计，不是实时监控状态）、
`data_plane`，以及与来源证据分离的可编辑描述性
`metadata`（`display_name`、`description`）。

完整的 Run、Case、Execution 状态枚举见下文。`ready` 执行必须具有
`DeploymentEndpoint`，包含 `url`、`protocol="http"` 和可选
`service_ref`、`model_ref`、`baseline_url`。端点元数据不得包含凭据、
kubeconfig 或授权值。

共享内存检查结果保存在
`artifact.rendered_payload.value.deployment_contract.sharedMemory`，并复制到
`diagnostics.value.snapshot.shared_memory`。报告包含 `defaultSizeLimit`（`4Gi`）、
`addedMounts`、各容器的 `mounts`、`warnings`，以及共享内存处理阶段的
`manifestChecksum`（在后续放置和追踪处理之前）。普通渲染会补充模型容器缺少的
`/dev/shm` 挂载；已有挂载和主机 IPC 设置保持不变。发布的 `officialGuide` 清单
只检查，不修改共享内存配置。警告也会写入日志；无效或重复挂载绑定会使渲染失败。
这不会修改传入的 Configuration 产物。

`get(execution_id)` 返回 `DeploymentExecution`，而非另一套状态 DTO。
具体服务查询内存中的执行状态，未知 ID 会抛出 `KeyError`，它本身不是数据库查询。
Worker/DAO 边界负责持久化记录并在需要时恢复执行上下文。协议还提供
`restore_execution`、`refresh_diagnostics`、`stop` 和 `clean`；
外部客户端应使用下方经过认证的 REST 操作。

`get_logs(DeploymentLogRequest(...))` 返回独立于执行元数据的 `DeploymentLogPage`：

- 请求字段：`execution_id`、可选非负整数字符串 `cursor`、范围 1 到 1000 的
  `limit`（默认 100）、`follow=False`、`sources=[]`。
- 当前来源为 `workload` 和 `events`，不是任意 Kubernetes 选择器。
  日志条目包含 `timestamp`、`source`、`message` 和可选 `severity`。
- 响应字段：`execution_id`、`entries`、`next_cursor`、`complete`、`evidence_refs`。
  `follow=True` 会设置 `complete=False`，但方法仍只返回一页，不是流式迭代器，
  也不保证等待新日志。
- 归档诊断由 `ExecutionLogArchive` 管理，引用格式为
  `deployment-log://<execution_id>/archive`。证据文件与数据库记录分开保留；
  参见[存储设置](/environment-variables)。保留的快照是局部诊断，不是完整集群日志历史。

### 消费方投影

这些是纯 DTO 辅助方法，不执行生命周期操作或 REST 权限检查。
`benchmark_input()` 要求执行处于 `ready` 且具有端点，否则抛出 `ValueError`；
输出执行 ID、产物、端点、命名空间和来源证据。
`simulation_input()` 接受任意执行状态，并额外输出部署状态和可选资源快照/端点；
它保留执行时的证据，不用当前可变集群状态替换。当前 Evaluation/Simulation
路由并不直接调用这两个辅助方法，不能将投影描述为它们实际的请求 API。

```python
from llm_d_lens.deploy.contracts import (
    BenchmarkDeploymentInput,
    DeploymentExecution,
    SimulationDeploymentInput,
)


def benchmark_projection(execution: DeploymentExecution) -> BenchmarkDeploymentInput:
    return execution.benchmark_input()


def simulation_projection(execution: DeploymentExecution) -> SimulationDeploymentInput:
    return execution.simulation_input()
```

## 后端 API

Guide 兼容端点保留 `{ "error": "..." }` 响应结构。
预期的校验失败保留可操作的错误提示及状态码。
目录加载和准备阶段的非预期错误返回通用 `502` 响应；
规划阶段的非预期错误返回通用 `500` 响应，并保留 `Server-Timing`。
异常详情仅记录在服务端日志中，不返回浏览器。

### 准备 Guide 源码

`POST /api/guide-planning/prepare` 接受 `guide`、`accelerator`、`modelServer`、
`guideVariant` 和选定的 `clusterId`。它准备官方源码但不部署，返回提交标识及从清单解析的能力：

```json
{"ready": true, "commit": "selected-source-commit", "capabilities": {"cacheCpuGiB": false, "rdmaNicCount": true}}
```

布尔值表示是否支持 CPU 缓存修改以及是否存在匹配硬件 profile 的 NIC 声明，
不依赖变体名称。处理函数为 `llm_d_lens.deploy.guide_planning.prepare`，
源码加载位于 `llm_d_lens.deploy.guide_sources`。部署提供方复用 `guide_overlays`
和 `llm_d_lens.hardware.resolver.deployment_mode(profile, access_mode)`。

当前单仓库启动和 Lens 存储根目录参见[安装](/installation)及
[存储环境设置](/environment-variables)。旧 `.llm-d-bench/deploy` 和主机专属的
`/root/.llm_d_lens/run_store` 不再是当前存储契约。
执行发现使用 `execution_id` 作为跨模块引用，列表查询不会建立端口转发。

execution 列表与详情 REST 响应还返回 `run_id`、`case_id`、`ownership`（`self`、`other`、`unknown`）
和 `capabilities`（`update`、`stop`、`delete`）。能力按当前调用者及写操作相同的 RBAC 规则计算，
仅供提示，写操作仍会重新鉴权；不会返回 owner 用户/组 ID。来源 run 存在时，详情中的
`configuration` 是按 case 的 `source_configuration_ordinal` 选出的完整 `DeployableConfiguration`。
这是保存的配置，不是从手动扩缩容后的现场状态重建的配置。
Python `ExecutionContext.api_payload()` 保持中立运行时投影；调用者相关字段由 REST router 添加。
需要主机可达地址时应调用执行端点连接操作，不能假定持久化的集群内地址或旧隧道仍然可达。

| 记录 | 生命周期状态 |
| --- | --- |
| Run | `queued`、`running`、`succeeded`、`partially_succeeded`、`failed`、`cleaned`、`cancelling`、`cancelled` |
| Case | `queued`、`rendering`、`deploying`、`ready`、`failed`、`stopped`、`cancelling`、`cancelled`、`cleaned`、`cleaned_up` |
| Execution | `draft`、`validated`、`rendered`、`deploying`、`ready`、`failed`、`rolling_back`、`rolled_back`、`cleaned`、`cleaned_up` |

停止的 Case 对应 `rolled_back` Execution，两者不是同一个状态枚举。
评测要求执行处于 ready、有端点且集群会话有效。下方 worker 示例在已配置的 Lens 后端内运行；
外部客户端应使用已认证的 HTTP，以执行路由权限和资源范围校验。

智能体创建和细化流使用 `llm_d_lens.agentic.streaming.planning_stream_response`。
这些路由保留了主体解析、预期错误分类以及它们现有的通用错误信息。
流会先发出 `progress`，然后是 `complete` 或 `error`；断开连接时的清理
操作会取消并等待尚未完成的规划。网关操作/日志流是单独处理的。

Agentic 的生成器和规划器用户消息均以完整用户偏好开头，随后才是 JSON 上下文。
提示词的优先级为：平台和硬件有效性、明确用户要求、软偏好、证据与候选多样性。
多样性不得引入用户禁止的拓扑，最终可以返回少于三个方案。
这是提示词约束，并不等同于服务端具备通用的自然语言硬约束解析能力。

规划快照（schema version 2）完整保留 `request.planner_prompt`，不做内容脱敏。
`planner_prompt_present` 仅作为兼容性标志保留，不再替代原文。
运行记录的 `generator_requests` 和 `planner_requests` 保存每一次实际 HTTP 尝试
最终发送的提供方原生请求体、原始响应、时间戳、HTTP 状态与错误类型，包括重试。
快照中对应字段为 `generator.requests` 和 `planner.requests`。
阶段审计文件位于 `session-artifacts/agentic-planning/<run_id>/requests/`，
在发送前和完成后落盘，因此取消、失败或未生成最终运行记录时仍可排查。
不记录认证头和 API Key；完整提示词和工具上下文属于私有应用数据。
审计只适用于修改后的新请求，无法补回过去没有记录的交互。

### Agentic 计划中的多来源证据

`AgenticDeploymentService.create()` 和 `.refine()` 使用实际请求主体解析证据，
REST 与流式调用均保留该身份。公开 Prism 观测按精确模型和实时硬件过滤，
要求全局 `benchmark-rag:query:read`；内部实验保留资源授权。
不信任客户端提交的公开观测和案例；包含公开观测的计划保留相同读取权限要求。

每次 `create()` 或 `refine()` 调用中，规划事实与公开证据检索复用同一份请求内硬件发现快照。
后续调用和批准部署会重新发现资源。加速器身份和可用显存仅来自实时自动识别，
不再支持 test-only 的硬件型号和显存环境变量覆盖。无法识别可用显存时会停止规划，
不会补入模拟容量。此前创建的模拟计划仍禁止部署。历史匹配使用部署运行时的服务后端；
公开记录的后端缺失、为空或为 `unknown` 时，SQL 匹配和返回的实验/案例上下文默认按 `vllm`
处理；明确标注的其他后端不会被重新归类。已存记录和原始来源证据不变，未知运行时版本仍保持未知。
提示词中的 TPOT 目标支持 `ms/token` 和 `s/token`，统一换算为毫秒。

基准数据比较按数值匹配等价的小数负载，将 `latency`/`e2e` 识别为端到端延迟别名，
并规范化 `p99p9`/`p99.9` 等小数百分位；原始来源证据仍保留。

服务端规范化显式负载和延迟要求，按配置和 series 聚合实验后，
每路 SQL 最多选择 50 个案例，再在 16,000 字节证据预算内保留最多 10 个完整案例。
显式负载匹配度优先，其次比较同口径的较低延迟；无负载时不施加负载惩罚。
缺失测量保持未知，不跨统计口径或实验拼出 SLO 结果。
既无可比较负载也无有效延迟的案例明确标注为回退参考。
只有所有请求的延迟指标及其统计口径都有对应数据时，候选才会获得 SLO 结论。
缺失指标保持 `unknown`，既不算达标，也不算失败。
仅有 TTFT/TPOT 证据不能证明端到端延迟目标，因此此类计划的 SLO 状态保持 `unknown`。

`planning_evidence` 使用 `id="public-rag:query"` 保存公开检索状态，
区分可用、无匹配、无权限和不可用。配置案例详情保留源条件、差异、未知项、
分支状态和截断信息。候选解释和服务端审计保持证据边界：
历史测量不能证明当前性能，AIC 仍为估算。

规划使用公开和内部 SQL 实验，不包含文档检索分支、embedding/向量检索或文档包契约。
模型提示词将来源称为公开基准证据和内部历史基准，并要求决策解释使用这些术语。
未包含在完整案例中的公开观测使用模型上下文字段 `published_benchmark_evidence`；
上下文为空只说明本次请求未提供证据，不代表数据库中没有数据。
已存储的 `public_rag_evidence` 字段、`public-rag:query` 证据 ID 和
`benchmark-rag:query:read` 权限保留为历史兼容标识，不代表具备文档检索能力。
原有私有诊断适配器不受影响。

创建校验已注册模型缓存存储卷，但不要求模型文件已下载；细化同样跳过下载就绪检查。
批准时要求缓存模型已就绪、解析当前凭据策略、刷新资源校验，并获得用户明确批准。

细化仅在重新核验了证据读取权限并保存新审计快照后，才会替换当前计划；
细化失败保留上一份计划。重算或批准期间计划发生变化时，需要重新加载后再操作。
手动选择备选候选会同步更新决策的 SLO 状态与证据，但不会改写先前的审计快照。
批准会在提交 Deploy 前离开 `awaiting_approval`，避免同一计划被重复提交。
提交失败或中断时，Agentic 运行标记为 `failed`；创建替代计划前应先检查部署运行记录。

部署相关功能位于 `llm_d_lens/deploy/router.py` 中的 FastAPI 路由下，
前缀为 `/api/v1/deployments`。

优化路由和精确路由的能力元数据复用了 `llm_d_lens.deploy.capabilities`
中的 `shared_prefix_routing_workload()`。每个场景和推荐的工作负载都会
获得各自独立的嵌套值；提供方专属的基线和目标保持不变。精确提供方的
校准和模型发现共享惰性的 modelserver 调用遍历逻辑，同时各自保留了
自己的"取最后一个值"和"取第一个模型"选择规则。

Agentic 候选提交接受 `optimized-baseline`、`pd-disaggregation`、`tiered-prefix-cache`
和 `precise-prefix-cache-routing`；生成器 schema 拒绝 `baseline-vllm`，规划器排序也会
排除它。AIC 聚合推荐映射到 `optimized-baseline`，包括负载目标和宽松锚点路径。

智能体规划会针对每个经过校验的 optimized-baseline 和
pd-disaggregation 候选方案，根据其工作负载和 GPU 拓扑结构，分别估算
缺失的精确 AIC 预测值。候选方案的估算值会以 `aic_estimate` 的形式
提供给 AI 评分；如果估算值不可用，则保持为未知状态，而不是一种
性能或 SLO 保证。智能体估算不会沿用原始搜索的 TTFT/TPOT 目标；
它们只是在没有 SLO 过滤的情况下，对固定的拓扑结构和工作负载进行校验。
当失败的生成器没有留下任何工具调用轨迹时，生成器回退逻辑也会使用
已解析的工作负载，对内置的前三个候选方案进行估算。不受支持或不可用的
拓扑结构保持为未知状态。宽松 AIC 搜索会接受任何不超过可用 GPU
预算的完整配置。它的预测结果并不能确立对原始 SLO 的符合性。
即使生成器只建议了一个更小的拓扑结构，智能体仍会将宽松的锚点方案
保留为一个经过校验的候选方案，然后估算其精确的拓扑结构和工作负载。
已知估算值未能达到原始延迟目标的候选方案会被标记为 `not_satisfied`；
在同样未达标的候选方案中，相对目标偏差更小的方案排名会优先于
GPU 节省量更大的方案。未知的估算值不会被视为失败。
当外部规划器对多个候选方案进行评分时，其选择理由会根据提供的
规划事实，解释为什么每一个评分较低的返回候选方案排在最高选择之后。
只有返回的前三个候选方案会被评分；对于该集合之外的候选方案，
不会推断出任何理由。

#### 共享估算契约（开发中）

独立的共享 Python 契约 `llm_d_lens.estimate_tools.models` 接受可选的
`Configuration.offload` 配置，例如
`{"tiers": [{"tier": "cpu_dram", "bytes": 1073741824}]}`。当前实现支持单个 CPU KV 层、
`OffloadingConnector`、`CPUOffloadingSpec` 或 `TieringOffloadingSpec`，以及 LRU 淘汰策略。
托管 BLIS profile 必须显式批准 CPU offloading；请求不能开启这项服务器权限。
当前不表达 NVMe 层、LMCache 连接器或连接器选项。关闭 offloading 时保留旧配置指纹，
开启时层容量会参与配置身份计算。

AISimulate 会显式拒绝该配置，不会忽略它。这不是旧版 `AICEstimateRequest` 或
`/api/v1/aic/*` 接口的新增字段。BLIS 拓扑、容量和 TTFT/TPOT 联合网格搜索仍是私有
Python 开发接口，尚未接入 HTTP、MCP、配置页面或 Agentic 调度。只有完整完成且满足
约束的已观测点才可成为推荐；模拟结果不代表预测准确性认证或部署批准。

联合搜索还接受总延迟目标 `latency_target_ms`。至少需要一种延迟目标，各指标统计口径
默认 p99；缺失原生证据时保持未知。省略拓扑网格时，按可用 GPU 预算及固定 PP/DP
生成有限候选，包括二次幂、设备预算边界和整节点 TP 分组；显式网格可覆盖自动生成。
配置推荐必须通过 `workload.request_rate` 或 `workload.concurrency` 指定一个业务负载，
所有候选均保留该负载，不接受负载网格，也不自动生成负载。
默认 `mode="economic"` 按满足目标后设备数最少、再按实测吞吐量较大排序；
`mode="performance"` 在设备预算内优先实测请求吞吐量，吞吐量相同时依次比较所选统计
口径下的 TTFT、TPOT、总延迟，再优先设备数较少的配置。固定 QPS 下，完整承载的候选
可能具有相近吞吐量，这不表示其容量上限。独立容量探测保持配置不变，扫描显式 QPS
或并发网格，仅报告已测试的可行负载，不排序或推荐配置。推荐结果包含设备数
及原生指标，只表示已观测候选中的最优点，不是全局最优或承载未声明负载的保证。
缺失的运行控制继承托管 profile 已验证的设置，不会虚构执行证据。

私有扫描结果通过 `execution_counts` 与 `constraint_counts` 分开统计执行状态和约束
结果，后者仅统计成功执行的点。网格遍历完成不表示配置可行，有限请求全部完成也不
证明持续承载业务负载。已执行点的 `execution` 保留执行元数据及原生 stderr 最后最多
4096 字节，无效 UTF-8 使用替换字符解码；`stderr_tail_truncated` 独立于执行输出上限
标记诊断尾部是否被截断。诊断在临时目录清理后仍保留，不参与点指纹。拓扑搜索通过
`execution_diagnostics` 按配置指纹保留失败执行元数据。原生 stderr 仅是诊断文本，
不是结构化容量结论；未知进程失败继续保持 failed／unknown，不根据内存相关措辞
静默判定配置不可行。

### 扩缩容部署执行

修改处于就绪或失败状态的执行的 Prefill 和/或 Decode 模型服务器实时副本数。此操作只修改 Kubernetes 副本数，不改变已保存的配置。支持 Deployment 和 DisaggregatedSet 工作负载。DisaggregatedSet 扩缩容只修改角色副本数，不修改 `spec.slices`；Lens 新建的 DisaggregatedSet 固定使用 `slices: 1`。

<Tabs>
  <TabItem value="rest-api" label="REST API">
    **`POST /api/v1/deployments/executions/{execution_id}/scale`**

    ```json
    }
    ```

### 刷新部署用例

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`POST /api/v1/deployments/runs/{run_id}/cases/{case_id}/refresh`**

不要求请求体，可发送 `{}`；需要 `deployment:case:execute`。
根据 provider 诊断刷新，返回 `200`，结构与获取用例相同，包含 `case`、`execution`、`deployment`。
已停止或已清理记录不会被重新标记为 ready。缺失用例／执行或刷新 `ValueError` 返回 `404`。

如果当前 Pod 诊断确认容器仍在探针预算内正常启动，即使报告进度期限超时也保持 `deploying`。

和探针时间字段，不包含容器环境变量值。仅有 Running 状态不会设为 `ready`；
当前工作负载失败或启动预算耗尽不会被视为正常启动。

```json
  "execution": {"execution_id": "execution-1", "status": "ready"},
```

路由存在，但当前 worker 清理旧执行并把用例标记为 `cleaned` 后，再调用
`DeploymentPlanService.retry_case()`；后者只接受最新的 `stopped` 或 `failed` 用例。
因此清理成功后仍会返回 `409`，而不是产生排队中的替代用例。
清理已经发生，错误并不代表旧资源仍然存在；不要反复调用此路由并期待恢复部署。

:::

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`POST /api/v1/deployments/runs/{run_id}/cases/{case_id}/restart`**

需要 `deployment:case:execute`、有效集群会话和 stopped／failed 用例。
请求体为 `RestartCaseRequest`，可选字符串 `model_token` 用于覆盖模型令牌，
空字符串／纯空白视为未提供；不覆盖时发送 `{}`。
声明的成功结构是 HTTP `200`、`{ "case": ... }`，但当前清理与重试状态冲突
使成功清理后的路径无法到达该响应。生命周期 `ValueError` 映射为 `409`，无效请求体返回 `422`。

```json
{}
```

当前冲突响应节选（应用另附 Problem Details 字段）：

```json
{
  "status": 409,
  "detail": "only the latest stopped or failed deployment case may be retried"
}
```

  </TabItem>
  <TabItem value="python-api" label="Python API">

```python

async def main() -> None:
    try:
        case = await deployment_run_manager.worker_for_run("run-1").restart_case(
            "run-1", "case-1", model_token=None
        )
    except ValueError as error:
        print(f"Restart failed; inspect the case because cleanup may have occurred: {error}")
        raise
    print(case.id, case.status)

asyncio.run(main())
```

## Remote SSH 部署

SSH 传输和远程命令失败返回 `502` 及
`{ "error": "Remote deployment failed" }`；内部异常详情及失败命令的输出
记录在服务端日志中，不暴露在错误响应中。
预期的输入和策略错误保留原有状态码及可操作的提示。

这些旧版端点由 Python 模块 `llm_d_lens.deploy.remote_deploy` 实现。
它们通过 SSH 执行命令，不创建 v1 部署运行。当前仅支持单节点 Intel Data Center GPU/XPU，
这是旧实现的限制，不代表由硬件 profile 驱动的 v1 API 的能力范围。

生产环境必须设置 `PRISM_REMOTE_DEPLOY_ENABLED=true`，非生产环境默认启用；
生产目标还必须匹配 `PRISM_REMOTE_HOST_ALLOWLIST`。
即使 SSH 操作被禁用，默认值接口仍可读取，但需要认证及相应权限。

| 操作 | Lens 权限 |
| --- | --- |
| Defaults | `remote-deploy:target:read` |
| Fingerprint、test | `remote-deploy:target:connect` |
| Start、status、logs | `remote-deploy:deploy:execute` |
| Teardown | `remote-deploy:deploy:teardown` |

需认证的 SSH 操作要求 `target.host`、`username`、`hostFingerprint`
以及非空、由数字 ID 字符串构成的 `cards` 数组。`port` 默认 22；
`authMethod` 默认 `agent`，还支持 `key`、`password`。
Agent 模式要求 BFF 有 `SSH_AUTH_SOCK`；key 模式要求服务端 `keyPath`
位于 `PRISM_SSH_KEY_DIR` 下，默认 `$HOME/.ssh`。
Password 模式在每次请求的 `credentials.password` 中提供密码，不保存也不返回。
指纹发现不执行认证，也不要求 cards。使用前应通过可信渠道确认指纹；
接口返回一个指纹本身并不能证明主机身份。

路由错误结构为 `{ "error": "..." }`：输入／凭据无效为 `400`，
生产目标不在允许列表为 `403`，SSH 操作被禁用为 `503`，
SSH／命令失败通常为 `502`。网关认证和权限错误使用网关的 Problem Details 格式。

### Remote 操作的 Python HTTP 客户端

这些 Node 端点**没有 Python 服务层等价方法**，下方 Python 页签使用此 HTTP helper。
示例环境变量只是客户端输入，不是新增的 Lens 服务端配置。
从已登录的 Lens 会话取得值，切勿提交其内容。

```python
import os
import httpx

def remote_request(method: str, path: str, body: dict | None = None) -> dict:
    with httpx.Client(
        base_url=os.environ["LENS_URL"],
        cookies={
            "prism_session": os.environ["LENS_SESSION"],
            "prism_csrf": os.environ["LENS_CSRF"],
        },
        headers={"x-prism-csrf": os.environ["LENS_CSRF"]},
        timeout=300,
    ) as client:
        response = client.request(method, path, json=body)
        response.raise_for_status()
        return response.json()

target = {
    "host": "192.0.2.20",
    "port": 22,
    "username": "operator",
    "authMethod": "agent",
    "hostFingerprint": os.environ["VERIFIED_SSH_FINGERPRINT"],
    "cards": ["0"],
}
```

下方 REST 请求示例展示操作字段；需认证的操作还要加入上述完整 `target`
以及可选的每次请求 `credentials`。Python 示例展示完整请求组装。

### 启动远程部署

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`POST /api/remote-deploy/start`**。以下操作字段还需加入 `target` 和可选 `credentials`：

```json
{
  "plan": {
    "namespace": "llm-d-optimized", "name": "llm-d-service",
    "accelerator": "Intel Data Center GPU", "nodes": 1,
    "guide": "optimized-baseline", "model": "Qwen/Qwen3-0.6B",
    "decodeReplicas": 1, "decodeTp": 1,
    "deploymentTarget": {"repository": "https://github.com/llm-d/llm-d.git", "branch": "main"}
```

namespace／name 默认如示例，必须符合 Kubernetes 风格名称。
repository 支持远程绝对路径、`~/` 路径或 GitHub HTTPS URL；branch 默认 `main`。
URL checkout 使用**远程主机**的 `LENS_CACHE_DIR`，否则为 `$XDG_CACHE_HOME/lens`

以及成对的绝对 `mountPath`／`mountModelName`。

Prefill TP／副本默认零。各维度必须为不超过 128 的整数，Decode 维度至少为一。
拓扑所需卡数不能超过所选卡数。卡 ID 会做格式和数量校验，
但此端点不保证物理设备绑定。显式 guide 必须是合法标识符；
未提供时根据 source／拓扑选择，不支持 `epd`。

## 配置准备 API

这些配置领域的路由会为部署和评估准备制品。请求和响应模型位于
`llm_d_lens.configuration.models`。示例中使用了用于说明的集群/会话
ID 和指南提交记录；请将它们替换为一个活动的集群会话和真实渲染过的
指南溯源信息。保存操作会发布一个制品；单独的渲染操作不会部署它。

流程为来源选择/编辑、resolve、render、save，最后才是部署。Resolve 先归一化各输入，
再进行能力检查与校验，并逐配置返回反馈。Candidate source 标识输入来源，不是部署类型。
Render 将候选意图与实际 Guide 资源绑定；save 发布不可变制品、身份信息与校验和。
Configuration 负责归一化、校验与制品发布，Deploy 负责运行时校验、资源生命周期、拆除与回滚。
校验和不能单独证明拓扑或资源语义正确。以下 REST 端点及 Python 服务函数遵循同样的边界。

HTTP 边界使用 `application/problem+json` 格式的错误。共享的
`DomainError` 实例会保留其原始的状态码和错误码（例如冲突仍然是
409）；它们不会被转换成一个操作专属的 500 错误。Python 服务调用
会抛出其原始异常；`llm_d_lens.configuration.router` 中的路由适配器
应用下面的 HTTP 映射关系。

## Agentic 实测优化

源码候选的 `resource_estimate.available_accelerators`、`checked_at`、`cluster_id`
和 `source` 保存资源检查时的容量快照。切换候选恢复对应快照；它不是资源预留，
也不是实时容量。审批仍会刷新容量，旧快照可能没有这些字段。

`POST /api/agentic-deployments/{run_id}/optimize` 返回 HTTP 202 和更新后的方案。
需要 Agentic 批准权限、压测创建权限、集群访问权限和有效会话。
`POST /api/agentic-deployments/{run_id}/optimize/cancel` 停止任务并清理其测试部署。
通过现有 `GET /api/agentic-deployments/{run_id}` 的 `optimization` 字段读取进度。

```json
{"candidate_ids":["candidate-a","candidate-b"],"objective":"throughput","max_gpu_count":8,"max_duration_minutes":60,"max_benchmark_runs":5,"repetitions":2,"confirmation_runs":1,"max_error_rate":0,"benchmark":{"matrix":[{"isl":512,"osl":128}],"concurrency_stages":[{"concurrency":4,"num_requests":100}]}}
```

Python 请求类型为 `llm_d_lens.agentic.optimization.OptimizationRequest`。
目标支持 `throughput`、`latency` 和 `throughput_per_gpu`。
可选 `native_cpu_cache_gib` 增加组合变体，其重复测试同样计入运行次数预算。
预算范围为 1–1024 GPU、1–180 分钟、1–30 次运行、每候选重复 1–3 次。
预算无效或不足时，在执行前返回 422。结果包含 `samples`、`ranking`、
`best_candidate_id`、状态和适用范围。仅完成、可比较且满足 SLO 和错误率上限的
测量进入排名；清理失败会明确显示并阻止批准部署。

矩阵和共享前缀测试必须收齐所有请求阶段。每轮采用各阶段中最高的 P95 延迟和错误率、
最低的 token 吞吐量作为保守边界，不将不同负载合并为总体 P95 或平均值。
缺失指标继续保持未知。

`confirmation_runs` 范围为 1–3，默认 1。候选比较结束后重新部署领先候选，
使用相同负载独立复测。`max_benchmark_runs` 默认 5，必须覆盖全部比较次数及复测。
独立复测记录保存于 `optimization.confirmation`，包含 `candidate_id`、`status`
和 `samples`。仅当复测满足 SLO、错误率上限且清理成功时才设置 `best_candidate_id`，
否则保持 null。复测失败时仍保留比较排名，但排名不代表已经确认的优胜方案。
外部 AI 可选，不能代替实测证据。

```python
from llm_d_lens.agentic.optimization import OptimizationRequest

request = OptimizationRequest(
  candidate_ids=["candidate-a", "candidate-b"],
  max_gpu_count=2,
  max_benchmark_runs=5,
  repetitions=2,
  confirmation_runs=1,
  benchmark={"matrix": [{"isl": 512, "osl": 128}]},
)
payload = request.model_dump(mode="json")
```

清理中断任务时，取消端点接受可选查询参数 `cluster_session_id`，必须指向原测试集群；其他集群会返回 HTTP 409。

`guideComposition.nativeCpuCacheGiB` 支持两种角色均使用内置 NixlConnector/kv_both 的 `pd-disaggregation`。适配器生成有序 MultiConnector 子连接器及相同镜像的能力检查初始化容器，保存的清单必须保留两者。实测优化中的 `native_cpu_cache_gib` 也会添加 P/D 变体。缺少适配器、镜像不匹配、角色缺失或缓存预算被修改均会校验失败。能力检查不能替代负载正确性测试和基准测试。
