## DS plan confirmation

Creating an Evaluation with deployable DisaggregatedSet cases now returns
`status="awaiting_review"` and `prepared_plans` instead of starting deployment.
Each case retains its frozen configuration, plan ID and digest. Existing endpoint
benchmarks retain their previous start behavior.

<Tabs>
<TabItem value="rest" label="REST API">

`POST /api/v1/evaluate/evaluations/{workflow_id}/confirm` requires
`evaluate:workflow:create`, exact workflow ownership and target cluster access. Submit the exact mapping of
**all** plan IDs to their reviewed digests:

```json
{"plan_digests":{"PLAN_ID":"sha256:REVIEWED_DIGEST"},"acknowledge_unknown":true}
```

Success returns HTTP 202 and the workflow in `queued` state. The existing sequential
executor consumes each frozen plan, rechecks preflight and records runtime evidence
plus a bounded request probe before benchmarking. Supported vLLM 0.26.0 NIXL pull
evidence proves only that probe, not the entire benchmark. Failed readiness/placement blocks the case; unknown
evidence is not a KV-transfer pass. A missing workflow returns 404; wrong status,
missing/changed plans, digest mismatch, failed preflight or unacknowledged unknowns
return 409. This is not resource reservation. No Slice Sweep is introduced.

`POST /api/v1/evaluate/workflow-runs/{workflow_id}/retry` returns HTTP 202. Succeeded
cases and reusable Ready executions are retained. Cases needing new reviewed deployments
receive fresh `prepared_plans` and status `awaiting_review`, not immediate execution.
Preparation failure returns 409 without overwriting the historical workflow. Otherwise
the workflow is queued. Task details expose the saved review for confirmation.
DS-derived automatic baselines record `content.comparisonBudget` with
`scope="accelerator-request-only"`, `resource`, `quantity`, `sourceRequests` and
`sourcePodCount`; the final baseline render must match that device quantity. Resource
budgets are preserved, but equal CPU/memory/Pod counts are not implied.

</TabItem>
<TabItem value="python" label="Python API">

The route callable is `llm_d_lens.evaluation.router.confirm_evaluation_plans` and
the body model is `llm_d_lens.evaluation.models.EvaluationPlanConfirmation`:

The retry callable is `await llm_d_lens.evaluation.router.retry_workflow_run(workflow_id)`
inside the established authenticated/owned workflow context. Inspect its returned
`status` and confirm new `prepared_plans` using the same function below.

```python
from llm_d_lens.evaluation.models import EvaluationPlanConfirmation
from llm_d_lens.evaluation.router import confirm_evaluation_plans

async def confirm_review(workflow_id, reviewed_plans, authenticated_request):
  body = EvaluationPlanConfirmation(
    plan_digests={plan["id"]: plan["digest"] for plan in reviewed_plans},
    acknowledge_unknown=True,
  )
  return await confirm_evaluation_plans(workflow_id, body, authenticated_request)
```

`authenticated_request` must carry the normal authenticated principal; internal
calls must not bypass route-level action/cluster authorization. The workflow control
lock protects confirmation from concurrent control actions.

Benchmark execution records may include `harness_pod_label` (the current CLI
invocation's unique app label) and `harness_pods` (Pod names mapped to UID, phase
and container states). The existing execution path in

## Harness proxy compatibility

Lens preserves HTTP(S) proxies for external downloads while forwarding cluster
addresses and CIDRs through `NO_PROXY`. Kubernetes Python client 35.0.0 can
discard that value, causing accelerator detection to send Kubernetes API requests
through the proxy and fail certificate verification.

Runtime preparation applies the known SDK correction to both the host CLI
environment and the selected checkout's harness Pod template. Newly created Pods
repair the affected client before starting the original harness command, including
warmup and matrix runs. Already-fixed clients remain unchanged; TLS verification
and download proxies remain enabled. An incompatible template or a failure to
write the affected container package stops startup with an explicit error rather
than running without the correction.

Existing Pods are not modified. A backend process without automatic reload must
load the updated code before starting a new evaluation; do not restart it while
it owns an active evaluation.

## Concurrent backend instances

Evaluation execution is protected by operating-system locks under
`LENS_DATA_DIR/metadata/evaluations/locks`. Backends sharing evaluation records
must share this directory on a filesystem supporting `flock`; sharing only the
database with independent data directories is not supported by this guard.
All participating backends must run the updated code. Separate development
installations should use independent databases and data directories.

Starting another backend does not mark a live owner's benchmark interrupted or
launch the same workflow again. Locks remain held through asynchronous cleanup
and are released automatically when the owning process exits. Automatic deployment
cleanup is deferred while a benchmark still uses the deployment. A delayed duplicate
executor cannot replay a completed workflow.

Cancel, retry, and delete requests targeting work owned by another backend return
HTTP `409` before changing records or cluster resources. Send the request to the
backend executing that evaluation. Local cancellation retains ownership until its
cleanup completes. The Python control callables enforce the same ownership checks.

## Backend API

Evaluation routes live in `llm_d_lens/evaluation/router.py` with the `/api/v1/evaluate` prefix. Request models are defined in `llm_d_lens.evaluation.models`; named HTTP response models are defined in `llm_d_lens.evaluation.api_models`.

Run, workflow, case, and detail responses preserve additional stored fields. Optional fields absent from the record remain omitted; explicitly stored `null` values remain `null`. List responses retain their `{ "items": [...] }` envelope. Python route functions return dictionaries; FastAPI applies the named response models at the HTTP boundary.

Errors use the application's `application/problem+json` response with `type`, `status`, `title`, `detail`, `code`, and an optional `requestId`. Client-error `detail` can contain structured validation errors; server-error `detail` is generic to avoid exposing internal exceptions. Authentication and resource permissions still apply; declaring a response model does not grant access.

### Agentic benchmark evidence

Existing run/detail REST responses and Python route dictionaries may include:

- `benchmark_context`: versioned test-time model, hardware and runtime metadata,
  source configuration checksum, capture/verification times and serving Pod identities.
- `benchmark_context_error`: why collection or topology verification was unavailable.
- `benchmark_model_metadata`: public descriptive model facts, API revision, lookup time
  and whether that revision was pinned by the serving snapshot.
- `benchmark_model_metadata_error`: best-effort public lookup failure, without failing archival.
- `benchmark_hardware_metadata`: explicit historical operator declaration, declaration
  time, configuration checksum and configured-card-count source; never a live observation.
- `benchmark_evidence`: ingestion status (`stored`, `partial`, `skipped`, `error`),
  eligible `record_ids`, `inserted_ids`, `existing_ids` and per-sample `issues`.
  Missing/invalid evidence is not reported as stored. An evidence-storage error does
  not change the original benchmark outcome.
  Its `metadata` section reports missing descriptors, snapshot availability and lookup errors.

No request fields are added. Both standalone and workflow benchmarks use the same
terminal ingestion path. Cancelled/setup-only runs are ineligible. Failed samples
require measured metrics, valid saved configuration/timestamps and an explicit failure reason.
Each matrix point/stage has its own stable evidence ID. Missing optional performance
metrics remain null; P95 values are read only from measured P95 distributions.
Family, architecture, parameter counts, device details and runtime versions are optional.
Each permanent record retains `provenance`; saved-configuration-only records are archived
but excluded from predictive matching. Unknown hardware/quantization never matches another
unknown value; missing runtime versions reduce similarity and confidence.

Python normalization and ingestion use the same saved run dictionary:

```python
from llm_d_lens.evaluation.benchmark_evidence import ingest_evaluate_run, normalize_evaluate_run

records, issues = normalize_evaluate_run(saved_run)
preview = ingest_evaluate_run(saved_run, apply=False)
```

Neither call fetches current metadata or substitutes planning estimates. Only
`ingest_evaluate_run(saved_run, apply=True)` appends eligible records. The administrator
CLI `python -m llm_d_lens.evaluation.benchmark_evidence` defaults to preview, supports
repeated `--run-id <uuid>` filters and requires `--apply` for writes. Preview reports
`eligible` rather than `stored` for new valid records and uses `eligible_ids` instead
of `inserted_ids`.
Add `--enrich` for public model API/config lookup before normalization; failures are
reported but do not block archival. Native lifecycle summaries are preferred over
standardized YAML, including exact sibling members in `workspace.tar.zst`.
Explicit historical hardware declarations require `--run-id` and all of
`--hardware-accelerator`, `--hardware-vram-per-gpu-gib` and
`--hardware-count-from-configuration`. Preview remains read-only; `--apply` persists
the declaration and normalized records without changing their archive-only attribution.

### Estimate benchmark timing

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`POST /api/v1/evaluate/timing-estimate`**

Accepts `BenchmarkSpec`, returns HTTP `200` with `BenchmarkTimingResponse`.
Requires `evaluate:run:read` and the normal session/CSRF checks. This is a pure
configuration preview: it does not access or launch a cluster resource.

```json
{
  "wait_timeout_seconds": null,
  "parallelism": 1,
  "shared_prefix": {
    "num_groups": 4,
    "num_prompts_per_group": 5,
    "system_prompt_len": 512,
    "question_len": 128,
    "output_len": 64,
    "stages": [{"rate": 0.4, "duration": 20}, {"rate": 0.8, "duration": 20}]
  }
}
```

For this input, `measured_requests` is 24, `lower_seconds` is 160,
`upper_seconds` is 340, and `timeout_seconds` is 900. The response also includes
`basis` (`configuration` or `unknown`), `confidence` (`low`), `phases` (per-invocation
lower/upper seconds), `timeout_mode`, `recommended_timeout_seconds`, nullable
`timeout_warning`, and the explicit `assumptions` used for the estimate.

Null or omitted `wait_timeout_seconds` selects automatic budgeting: 1.5 times the
largest invocation's upper estimate plus 120 seconds, bounded to 900-14400 seconds.
Explicit values from 1-14400 remain manual hard limits. Unknown workload timing
returns null estimates/counts and an empty phase map, with a 7200-second automatic
fallback. Supported estimates cover generated single-turn shared-prefix and
explicit matrix/concurrency workloads with inference-perf; custom YAML and
repository profiles remain unknown. Invalid input returns `422`.

  </TabItem>
  <TabItem value="python-api" label="Python API">

```python
from llm_d_bench.deploy.capabilities import shared_prefix_routing_workload

```

it uses the same pure function as `create_run`.

### Start a benchmark run

Both REST `create_evaluate_run` and Python `create_run(EvaluateRunRequest(...))`
require serving monitoring readiness before starting traffic. Preparation uses
the resolved `wait_timeout_seconds` budget (600 seconds for legacy records with
no budget); this is separate from each benchmark invocation's execution limit.
Every discovered serving Pod needs `up=1` and two inference gauge samples, and a
discovered EPP service needs a healthy target. Setup errors or timeout fail the
queued run before traffic. Poll run details for `phase=preparing-monitoring`,
`heartbeat_at` and `monitoring.message`; HTTP submission still returns 202.

Recorded `metrics.observability.status` retains its aggregate sample-availability
meaning. `flow_status` and `flow_reason` separately describe request/token sample
availability. `monitoring.status=partial` means resources were saved but traffic
samples are absent; `monitoring.preparation` retains the preflight evidence.
For example: `{"status":"available","flow_status":"unavailable","flow_reason":"No inference request or token samples were recorded during the benchmark window. Resource samples do not establish serving traffic monitoring."}`.

Start a benchmark run against a ready deployment execution or a published Model Service.

Both configuration-driven workflows and existing-service benchmarks call
`create_run()` and the same executor; workflows add deployment orchestration and
comparison. The current UI selects a published Model Service for the existing-target
flow, not an arbitrary URL. `deployment_ownership` controls cleanup, not metric
semantics: cancelling an existing-service benchmark does not stop the model service.

Both use `BenchmarkSpec` defaults: `parallelism=1`,
`wait_timeout_seconds=null` (automatic), `harness_memory_gib=8` per worker, and
`warmup_requests=2` for a matrix. Explicit settings take precedence; the UI's
preset warmup may differ. Legacy callers needing 7200 seconds or 32 GiB must
request those values explicitly.

| Evidence operation | Current behavior |
| --- | --- |
| Monitoring preparation | Reuse a healthy Prometheus target (`up == 1`); otherwise attempt monitor resources and supporting RBAC. Discovery, setup and readiness share a 30-second deadline. Failure is recorded, not a benchmark failure. |
| Prometheus collection | Query the benchmark window even after setup failure, with a 120-second deadline. Discover the cluster's central Prometheus; do not infer an external Prometheus URL from the model endpoint. Missing series remain unavailable, not zero. |
| KV capture | Use already instrumented containers, starting/stopping capture via `kubectl exec`. Benchmarking never installs probes, changes model manifests or restarts the service. Unsupported layouts, missing probes/request IDs, capture conflicts or worker parallelism other than one produce unavailable evidence. |
| Resource snapshots | Capture completion-time resources before cleanup, best-effort with a 30-second deadline. A missing historical snapshot is not replaced by current live resources. |

Probe installation is a separate deployment-rendering step: eligible new vLLM
manifests receive instrumentation; the current injector skips PD manifests.
An existing instrumented deployment can be measured without redeployment.
KV working-set collection requires compatible vLLM V1, prefix caching, a single
FullAttention cache group and `parallelism=1`. It measures deduplicated complete
prompt blocks from successful requests, excluding generated tokens and incomplete
trailing blocks. Missing records or incomplete request association produce an
unavailable result; whole-run evidence is not automatically assigned to individual
load stages. Equal workloads and instrumentation provide the same metric coverage
and semantics, not guaranteed identical measurements.

For operator steps, see [Choose an evaluation Guide](/evaluation/guides).

`EvaluateRunRequest.accelerator_profile` accepts registered IDs and aliases, including
IDs without dots. When omitted, the execution's configuration supplies the profile.
The benchmark worker records a `hardware_profile` snapshot and adds its declared
device metrics to `monitoring.timeSeriesMetrics` in llm-d-benchmark. The Python
`create_run` route below applies the same resolution and validation as REST.

`wait_timeout_seconds` now defaults to null (automatic), while explicit numeric
limits remain unchanged. `create_run` stores the original intent in `benchmark`,
the resolved integer at the run's top-level `wait_timeout_seconds`, and the
configuration estimate under `timing`. The CLI wait and Lens subprocess deadline
use the same resolved limit per invocation. `benchmark_started_at` records the
first subprocess start; `phase_started_at` resets for warm-up and each matrix
point. Run/detail responses retain these fields. Failed historical runs are not
reconfigured automatically. Both REST and Python `EvaluateRunRequest` calls use
this behavior.

### Get a benchmark run

and adds known `configuration`, `deployment_configuration`, model/namespace/endpoint
context and read-only `deployment_cases`. These links do not grant lifecycle ownership.

capacity/SLO, mechanism and diagnostic enrichment with workflow results.
Saved client reports can support historical backfill; missing historical
Prometheus samples, KV captures and resource snapshots cannot be recreated from
current live data. Rerun to collect newly enabled evidence.

### Start a multi-configuration evaluation

Start a multi-configuration evaluation workflow that can deploy, benchmark, compare, and optionally baseline several published configuration artifacts.

For a `pd-disaggregation` source, independent baselines match the total prefill
plus decode GPU budget by default:

```text
baseline replicas = (prefill replicas * prefill TP + decode replicas * decode TP) / baseline TP
```

Baseline TP inherits source decode/serving TP unless
`benchmark_plans[].baseline_parameters[baseline_type].tensor_parallel_size`
overrides it. A TP-only override recalculates replicas; explicit `replicas` wins
and permits an intentionally unequal budget. For example, 2P2D at TP=1 produces
four plain-vLLM replicas at TP=1, or two at baseline TP=2.
Automatic matching must yield an exact integer in `1..32`; otherwise creation
returns `409` before saving or queueing, without rounding or capping.
Non-PD sources inherit decode/serving replicas; same-pod `kubernetes-service`
comparisons reuse the candidate pool without independent replicas.
These defaults apply to new evaluations, not stored/running snapshots or retries.
An old unequal-budget comparison does not become equal-budget retroactively.
See [Evaluation parameters](/evaluation/parameters) for override ranges.

### Get detailed evaluation workflow results

The linked benchmark and case results use the same enrichment as standalone
benchmark detail. Case snapshots are saved completion-time evidence.
`deployment_cases` may additionally include current Kubernetes snapshots for
inspection; those live snapshots are not historical benchmark measurements.

Get expanded evaluation workflow results and deployment links.

For workflows with cases, the report uses `comparison_version: 2`. Older cached reports are regenerated from retained evidence when details are read. Matrix rows match unique successful `(isl, osl)` points and explicit `concurrency`; rate stages match explicit `rate`. Missing, non-finite, negative, or duplicate load keys do not establish a match, and array position is never a fallback. No matched rows means the corresponding statistics are `null`.

Ratios are guide divided by baseline. A valid zero numerator is retained, including in the geometric mean; a zero denominator yields no ratio. Suite-normalized throughput uses only matched pairs where both sides have nonnegative output-token counts and positive measured durations. Mean, P90, and P99 aggregates remain separate.

### Benchmark monitoring clock alignment

`metrics.observability.clock_alignment` records `status` (`measured` or
`unavailable`), `offset_seconds` (Prometheus minus Lens time, or null), and
`query_window` (`start`, `end`) used for the Prometheus range queries. The original
`window` and persisted series timestamps stay on the Lens timeline, including
rate-stage slicing. If clock measurement fails, collection retains the original
window and reports alignment as unavailable.

The existing Python callable
`llm_d_bench.monitoring.profiling.service.collect_benchmark_observability(execution_id, start, end, cluster_id=None)`
performs this alignment without changing its signature. For example:

```python
from llm_d_bench.monitoring.profiling.service import collect_benchmark_observability

observability = await collect_benchmark_observability(
    execution_id="deployment-id",
    start="2026-10-09T09:50:00Z",
    end="2026-10-09T09:55:00Z",
    cluster_id="cluster-id",
)
print(observability.get("clock_alignment"))
```
