## Reviewed DisaggregatedSet plans

DS, resource-budget and inferred equal-device baseline configurations require preparation
and explicit digest confirmation. Preparing does not
create a Run or Kubernetes resources. The plan is owner- and cluster-bound, stores final
workload YAML, namespace, Router values and a checksum-verified local Chart archive, and
is consumed atomically with Run creation. Repeating the same successful confirmation
returns the original Run. Changing configuration, runtime settings or cluster requires
a new plan; renewing only the session for the same cluster does not.

| Endpoint | Contract |
| --- | --- |
| `POST /api/v1/deployments/plans` | Accepts `DeploymentRunCreateRequest`. Requires create permission, active target session and cluster access. Returns `id`, `digest`, `clusterId`, `status`, `createdAt`, `runId`, `preflight`, and `cases`; invalid inputs return 422. |
| `GET /api/v1/deployments/plans/{plan_id}` | Requires read permission, exact plan ownership and cluster access. Returns the saved review view, not refreshed preflight; unavailable plans return 404. Archive bytes and local paths are excluded. |
| `POST /api/v1/deployments/executions/{execution_id}/restart-plan` | Requires run-create permission, case-execute scope and cluster access. Optional body `{"cluster_session_id":"SESSION_ID"}` renews the same-cluster session with session-rebind permission. A stopped/failed prepared execution returns `{"status":"awaiting_review","plan":{...},"request":{...}}`; unsupported or Evaluation-owned executions return 409. No cleanup or execution occurs. |
| `POST /api/v1/deployments/runs` | Submit the original request plus `prepared_plan_id`, `expected_plan_digest`, and `acknowledge_unknown`. Rechecks preflight and refuses changed bindings, failed constraints or unacknowledged unknowns with 409. |
| `GET /api/v1/deployments/topology?cluster_id=ID` | Requires create permission and cluster access. Returns Node labels, allocatable resources, conditions and taints, plus Pod node, phase and effective `resourceRequests`. Unavailable/incomplete inventory returns 503. |
| `POST /api/v1/deployments/executions/{execution_id}/verify` | Requires case-execute scope and cluster access. Body `{"smoke":false}` reads evidence; `true` also sends bounded inference and may establish a port-forward. Returns independent `kubernetes`, `placement`, `routing`, `kvTransfer`, `pods`, `observedAt` and optional `inference`. Unsupported executions return 409; unavailable cluster evidence returns 503. |

After preparing an existing deployment request, retain it unchanged and add:

```json
{
  "prepared_plan_id": "ID returned by preparation",
  "expected_plan_digest": "sha256:digest returned by preparation",
  "acknowledge_unknown": true
}
```

Each review case includes `manifest`, `namespaceManifest`, `manifestChecksum`, `namespace`,
`routerManifest`, `routerValues`, `chartChecksum`, auxiliary `resources` and `sourceCommit`.
`storageResources` contains reviewed satellite PV/PVC manifests; changed storage definitions
or existing PV name collisions are rejected. `secretReference` identifies the configured
credential source without its bytes; this does not freeze credential rotation. Unsupported
dynamic-PVC mirroring into a new deployment namespace is rejected during preparation.
`preflight.status` is `pass`, `fail` or `unknown`. A modeled
placement witness is not a reservation: admission, quota, concurrent scheduling,
rollout surge and unsupported constraints remain unknown. Unknown acknowledgment
does not override a failed constraint.
`preflight.assignments` entries carry `domain` when the placement policy uses a topology
key. `preflight.slicePreview` lists one entry per DisaggregatedSet case with `caseIndex`,
`workload`, `slices`, `maxFeasibleSlices` (free-resource estimate for the case's policy;
`null` when unknown), `placementPolicy`, `sliceRouting` (`prefer` when the frozen Router
values contain the affinity scorer), `roles`, `sliceRequests`, `acceleratorResources` and
`placement` (modeled Pods per Slice with node and domain).

Cases also expose optional `comparisonBudget`. The existing case
restart endpoint returns the same review response for prepared deployments and rejects
inline model tokens; rotate the configured Secret source instead. Submit the returned
`request` plus the new plan ID/digest to `POST /runs`. Old resources remain untouched.
Smoke verification adds `captureErrors`, `after`, and an `artifact` inventory with
immutable report checksums. Passive reads return `lastProbe` when one is saved.
The verify request also accepts `metrics_only` (mutually exclusive with `smoke`): it reads
current per-Pod model-server metric counters without sending any inference request or
persisting a report, returning `metrics` keyed by Pod name plus `metricsCollectedAt`.
Counter values are snapshots at collection time, not rates.

`llm_d_lens.deploy.prepared_plans` exposes `prepare(manager, request, owner_user_id=...)`,
`public_plan(plan)` and `consume(manager, request, owner_user_id=...)`. These internal
callables assume the HTTP caller has enforced action permission and cluster access.

```python
from llm_d_lens.deploy.contracts import DeploymentRunCreateRequest
from llm_d_lens.deploy.prepared_plans import prepare, public_plan, consume

async def prepare_for_review(manager, request_body, owner_user_id):
  request = DeploymentRunCreateRequest.model_validate(request_body)
  plan = await prepare(manager, request, owner_user_id=owner_user_id)
  return public_plan(plan)

async def execute_reviewed(manager, original_body, reviewed_plan, owner_user_id):
  request = DeploymentRunCreateRequest.model_validate({
    **original_body,
    "prepared_plan_id": reviewed_plan["id"],
    "expected_plan_digest": reviewed_plan["digest"],
    "acknowledge_unknown": True,
  })
  return await consume(manager, request, owner_user_id=owner_user_id)
```

The authenticated route callables support restart preparation and verification:

```python
from llm_d_lens.deploy.router import (

async def review_restart(execution_id, authenticated_request):
  return await prepare_execution_restart(execution_id, authenticated_request)

async def probe_execution(execution_id, authenticated_request):
  return await verify_deployment_execution(
    execution_id, RuntimeVerificationRequest(smoke=True), authenticated_request,
  )
```

Verification reports observed ownership and Node topology, not physical-fabric
certification. HTTP success and aggregate metric deltas do not prove request-specific
P/D routing or KV transfer; those dimensions remain unknown without correlated evidence.
For instrumented vLLM 0.26.0 NIXL pull workers, a positive verdict requires a unique
response-to-decode request mapping, remote producer request identity, nonempty receive
completion and producer acknowledgements for every TP rank, stable Pod/engine identities,
matching DS ownership/revision and no observed failure/recompute fallback. Evidence
records actual Pod UIDs, same-Slice/domain observations and block counts. A cross-Slice
pair is observable evidence, not a violation of the soft routing preference. Other
versions/connectors, missing ranks, full-cache-hit notifications without transfer and
incomplete capture remain unknown. This certifies only the bounded probe request.
Frozen execution skips Helm CRD installation and hooks. Install compatible controllers
and CRDs separately. Review accepts only classified namespaced resource kinds, rejects
embedded Secret objects (including nested Lists), and rejects other namespaces.
The only separately generated cluster-scoped resources in this plan are the reviewed
storage satellite PVs; arbitrary cluster-scoped YAML is not accepted.
Namespace ownership markers guard cleanup against deleting a
pre-existing or replaced namespace.

### Guide configuration inputs

The UI-only `POST /api/guide-planning/prepare` accepts `guide`, `accelerator` and
`modelServer`, and returns `ready`, full `commit` and `capabilities.disaggregatedSet`.
For DS sources with optional `clusterId` and `model`, `recommendation` contains
`guideDefault` (`slices`, `placementPolicy`), `capacity` (`sliceRequests`,
`acceleratorResources`, `podsPerSlice`, `maxSlices.None`, `schedulableNodes` and
`topologyKeys` with per-domain `domainDetails`, `feasibleDomains` and
`exclusiveTopologyDomains`, and `unmodeled`, which lists `DRA` when Slice Pods request
accelerators through ResourceClaims that the estimate does not count), a suggested `placementPolicy` with `maxSlices` and `reasons`,
and `history` of recent succeeded same-model Evaluation cases on that cluster
(`slices`, P/D shape, `accelerators`, `maximumStableQps`, `throughputTps`, `accelerator`,
`guideCommit`, `slaTargets`, `workloadLabel` and `evidenceKey`, which groups runs with the same
request shape and SLO targets regardless of rate stages). It never selects a Slice count; capacity is estimated for the Guide default
roles and is not a reservation.
`POST /api/guide-planning/plan` additionally accepts `expectedSourceCommit` for official
sources and `disaggregatedSet`:

```json
{"disaggregatedSet":{"slices":2,"placementPolicy":{"type":"ExclusiveSlice","topology":"topology.kubernetes.io/zone"},"sliceRouting":"prefer"}}
```

The planner returns `disaggregatedSet` and `workloadSummary` with expanded Pod count and
resource requests. With a cluster session, DS plans also return `sliceCapacity` (the same
shape as `recommendation.capacity`, computed for the rendered roles; `null` when inventory is
unavailable). Role replicas are **per Slice**; group size expands leader/worker
Pods, and resource requests, not tensor parallelism, determine demand. Legal multiple
Slices are retained. External scaling with multiple Slices is rejected. `sliceRouting`
is `inherit` or `prefer`; the latter requires supported llm-d Router 1.0 single-EPP
profiles and adds a soft prefill affinity scorer, not a strict routing guarantee.
Official and remote custom sources render from fixed Git snapshots; external Kustomize
dependencies must be vendored. Local inputs and referenced files are copied before
rendering. Local provenance uses `revisionKind="content-snapshot"`, `snapshotChecksum`
(SHA-256) and its first 40 hex characters in `commit`, not the dirty tree's Git HEAD.
`POST /api/v1/configurations/render` accepts `candidate_config.disaggregated_set`,
stored as `content.disaggregatedSet`. `workloadSummary`
also includes a `disaggregatedSet` boolean for custom-source capability discovery.
Python callers use `CandidateConfig`/`GuideSource` in `llm_d_lens.configuration.models`
and `render_configuration(RenderRequest.model_validate(request_body))` in
`llm_d_lens.configuration.service`; the same fields and validation apply.

The Python route callables are `llm_d_lens.deploy.guide_planning.prepare(request)` and
`plan(request)`; both take a Starlette `Request` carrying the JSON body and established
cluster/session context. Prefer the browser workflow for these UI-only endpoints.

When specifying an operator preference for deployment planning, use English, such as
`prefer prefix cache`, `more GPU for performance`, or `use fewer GPU resources`.
The deterministic planner matches English preference keywords; Chinese keyword aliases
are no longer supported.

## Python domain contracts

### Shared Manual / Agentic planning

The new creation UI uses the existing Agentic run lifecycle for both decision
modes. Legacy requests without `requirements` keep their existing behavior.

<Tabs>
<TabItem value="rest-api" label="REST API">

**`POST /api/agentic-deployments`** returns `201` with an
`AgenticDeploymentRun`. The browser's `/stream` variant returns progress and
the same completed run over SSE. Neither operation deploys resources.

In addition to the Standard serving and active-session fields:

- `planning_mode`: `manual` or `agentic` (default). Manual is the rule-based planner and never initializes an external AI planner.
  Agentic requires a resolvable AI provider (`ai_provider_id`, or the server environment provider) and returns `422`
  without one. If AI candidate generation or ranking fails, the request fails instead of falling back to rules.
- `requirements`: model and cluster identity, objective, `hard_constraints.maxAccelerators`,
  workload, performance targets, required/forbidden mechanism IDs and unknown fields.
  Legacy mechanism IDs `pd_disaggregation`, `prefix_routing`,
  `external_kv_cache`, `prefix_cache` and `chunked_prefill` remain supported.
  Source composition also accepts catalog mechanisms such as `index` (precise
  routing), `load-routing`, `wide-ep` and `speculation`; these must be established
  by the final resources, not merely requested. `affinity` and `index` are distinct.
  Objective defaults to `balanced`; latency, throughput, cost and reliability
  remain supported. Missing workload fields stay unknown.
- `requirements.hard_constraints.providerRef`: optional explicit provider recipe.
  Supported recipes are `optimized-baseline`, `pd-disaggregation`,
  `precise-prefix-cache-routing` and `tiered-prefix-cache`. Other recipes are
  rejected; mismatching candidates are excluded at planning, revision and approval.
- `requirements.workload.p95InputTokens`: optional positive input-length percentile,
  independent of mean `inputTokens`; omission stays unknown.
- `requirements.performance_targets.e2eMs`: optional positive integer end-to-end
  P95 latency target in milliseconds, alongside `ttftMs` and `tpotMs`. Trial ranking
  requires every completed repetition to satisfy configured targets.
- `planner_prompt`: optional AI goal. With an explicit `ai_provider_id`, missing
  `prefixReuse` and `prefillHeavy` traits can be extracted from explicit statements
  in any language. Structured values take precedence. Added traits set
  `workload.interpretationSource=ai_goal`; interpretation failure returns `422`.
  Numeric limits are not inferred. Manual does not call an external AI provider.
- `planning_facts.max_candidates`: Agentic retained-candidate limit, 1–10.
  Manual preserves each distinct supported capability family even for a smaller limit.
  Live free resources override client-supplied hardware facts.
- `execution_policy.max_total_duration_minutes`: planning deadline, 1–180.
- `execution_policy.allow_trials`: defaults to false. Enabling it permits a later,
  separately approved `/optimize` request; it never starts testing during planning.

```json
{
  "model": "Qwen/Qwen3-8B",

  "cluster_session_id": "00000000-0000-0000-0000-000000000001",

  "storage_volume_id": "registered-cache-id",
```

Replace the example IDs with an active session, its actual cluster and a ready
model cache. Invalid identities, unsupported constraints, unknown required
mechanisms and infeasible resource limits return `422`.

The response includes `configuration_plan`, `revision` and optional `parent_run_id`.
The shared plan retains requirements, mechanism decisions, resource estimates,
the exact deployable `configuration`, and separate completed/pending checks.
`planning_checked` does not mean manifests, admission or performance passed.

`configuration_plan.optimization_choices` lists the five user-selectable optimizations
(`prefix_routing`, `prefix_cache`, `chunked_prefill`, `external_kv_cache`,
`pd_disaggregation`) with `checked` (false when listed in `forbidden_features`), `auto`,
`intended` and `reason`. A checked optimization whose final decision is not enabled was
degraded. P/D is on by default with at least two usable accelerators. When Manual
receives mean `inputTokens` and `outputTokens`, it compares AIC's best P/D and combined
predictions (meeting `ttftMs`/`tpotMs` first, then throughput) and records the result in
`requirements.workload.aicPrefillDecode` and `aicPrefillDecodeReason`; without an AIC
result P/D stays on. Manual also sets each candidate's `slo_status` from the AIC prediction
for that exact topology. It ranks candidates by SLA status, then the P/D decision, then
checked optimizations, keeps SLA misses (ranked last) instead of failing, and never selects
`precise-prefix-cache-routing`. With a load target, both modes size topologies from AIC
when it supports the model and hardware.

**`POST /api/agentic-deployments/optimizations/preview`** returns the same
`optimization_choices` for a `requirements` body and an optional caller-reported
`available_accelerators`. It is pure computation with no cluster access and requires
`deployment:agentic:read`.

For both modes with structured requirements, planning also expands native CPU
KV-cache adapters for baseline, precise routing and P/D. Standalone tiered cache
is sized through `guideSettings.cacheCpuGiB`; compositions use
`guideComposition.nativeCpuCacheGiB`. Each serving replica receives at most
8 GiB; total cache allocation is at most 25% of observed free host memory.
Unknown memory does not authorize an automatic cache allocation.
`resource_estimate.cpu_cache_gib` records the total. Planned cache decisions stay
`unknown` until source-bound rendering succeeds. Sequence count is clamped to
the selected model/VRAM concurrency estimate when available in Manual.

Unknown workload shape or prefix reuse never rejects a technically compatible
candidate. `prefix_routing` is an independent nullable Boolean on candidates:
`true` composes source-established affinity plugins into the default/prefill
scheduling profile, `false` removes affinity while retaining load routing,
and `null` preserves legacy provider routing. Generated configuration carries
`prefixRouting`; the same option is consumed by the shared Guide renderer.
The saved bundle retains `router-prefix-source.yaml` and validates effective
values against that source, preserving P/D handlers and decode profiles.

Manual always enumerates every registered provider topology, even with a concurrency
target; AIC load-target recommendations are Agentic only. Manual excludes known SLO
misses, then ranks mechanism coverage first, then whether replicas admit the concurrency
target, then the objective:
throughput prefers P/D then prefix routing; latency prefers prefix routing;
cost prefers fewer accelerators; reliability prefers multiple serving replicas.
The default `balanced` objective and remaining ties prefer fewer accelerators. Retained alternatives favor recipe/cache
diversity, including independent routing choices. Rationale exposes this policy, not a measured optimum. Cache and routing compositions
do not inherit performance evidence from their uncomposed topology.

#### Full Guide source composition

The integrated editor uses the selected cluster's pinned sources rather than
five hardcoded optimization controls:

- **`GET /api/guide-planning/source-catalog?clusterId=...`** returns `commit`,
  `guides`, selectable `assets`, source parameters and `optimizations.items`.
  The catalog contains the shared mechanism definitions and additional discovered
  Guides. Presence does not establish compatibility or an executable adapter.
  `environment` preserves literal exports and literal `${VAR:-default}` values
  from `guides/env.sh`, including chart version pins. Shell commands and dynamic
  expressions are not evaluated.
- **`POST /api/guide-planning/source-preview`** takes `clusterId`, `commit` and
  `unit` (including its catalog `path` and optional typed edits). It renders a
  component and returns its documents and observed optimization flags.
- **`POST /api/guide-planning/compose`** takes the pinned `commit`, `clusterId`,
  `clusterSessionId`, `namespace`, `modelCacheEntryId`, `units` (1–60), optional
  `router`, `guideSelection`, `deploymentIntent` and `finalConfiguration`.
  `finalConfiguration` binds edited YAML to the previous `baseChecksum`.
  It returns `files` (`deployment.yaml`, `provenance.json`), effective
  `optimizations`, `compositionChecksum`, and separate resource/admission validation.
  DRA sizing supports generated `ResourceClaimTemplate` resources with `ExactCount`
  requests. Counts follow each role's tensor parallelism, replicas and autoscaler
  ceiling; non-accelerator requests remain unchanged. Availability uses the matching
  cluster profile's usable-device inventory. External claims, ambiguous allocations
  and mixed-profile availability are rejected; device selectors, NICs and placement
  still require admission and runtime validation.
  Automatic hard P/D slice placement adds required node affinity for domains that
  fit a complete slice, listed in `sliceLayout.recommended.eligibleDomains`.
  Existing affinity is preserved. Explicit slice policies are not replaced, and
  these checks do not reserve devices; regenerate after capacity changes.
  Optional `validateCluster` runs a server admission dry-run, not deployment.
- **`POST /api/agentic-deployments/{run_id}/composition`** persists that result
  into an idle deployment plan. Submit the current `revision`, `compare`, and
  `candidates`, each containing `candidate_id`, restorable `draft` and composer
  inputs in `composition`. A proposal may instead carry an explicit `error`.
  `compare=true` must account for every retained candidate. Manual selects maximum
  final-manifest coverage among passing proposals; Agentic retains its selected
  recommendation when valid, or explicitly reports a validated fallback.

Successful plan composition increments `revision`, invalidates old approval and
performance evidence, and stores `source_bundle`, `source_draft`, `source_request`,
`source_candidates`, and selectable Service `endpoints` in `configuration_plan`.
`configuration.checksum` is the review token for the generated deployment YAML.
Decisions carry `catalog_id` as well as legacy-compatible `capability_id`.

All source operations require `guide:plan:execute` and authorized cluster access;
plan composition also requires `deployment:agentic:create`. Model-cache and
storage reads keep their existing permission checks. No Guide shell script runs.
Stale source/editor revisions return `409`; invalid composer inputs return `400`;
failed plan comparisons return `409` without replacing the previous plan.
Rendering deadlines return `504` for plan composition.

Approval additionally requires `endpoint`, an exact value from the reviewed
`configuration_plan.endpoints`:

```json
{
  "configuration_checksum": "sha256:reviewed-deployment-yaml-checksum",
  "endpoint": "reviewed-inference-service:8000"
}
```

Approval rechecks the cache binding, available devices, memory and required/forbidden
mechanisms, then uses the existing managed deployment lifecycle. Source snapshots
use `runtime.modelSource=cached-readonly`; ordinary `auto-cache` contracts remain
unchanged. Multi-node model roles and cluster-scoped provisioning without a managed
lifecycle remain blocked, with explicit errors rather than partial deployment.
The bounded exception is Router authentication RBAC: ClusterRoles may only create
TokenReviews and SubjectAccessReviews, with bindings to the generated EPP
ServiceAccount. Runtime names are deployment-specific; creation binds ownership to
the namespace UID and never overwrites foreign or changed objects. Namespace cleanup
garbage-collects these exact resources and waits for their removal; incomplete
collection is reported as cleanup failure. Other cluster-wide grants remain blocked.
Stopping a source deployment removes its HPA/KEDA autoscalers before scaling model
controllers to zero; deploying the reviewed snapshot again recreates those autoscalers.
Source-backed `/optimize` requests also supply `endpoints` keyed by candidate ID;
trials use the reviewed source candidate resources, never a substitute base recipe.

Reviewed source candidates retain `resource_estimate.available_accelerators`,
`checked_at`, `cluster_id` and `source` from their resource-check snapshot. Candidate
selection restores that snapshot. It is not a reservation or a live capacity value;
approval still refreshes capacity. Older snapshots may lack these fields.

**Legacy `POST /api/agentic-deployments/{run_id}/select`** returns `200`:

- `{"candidate_id":"..."}` selects an already validated alternative.
  For source plans this restores that candidate's exact reviewed resources and editor
  parameters, increments the revision, and resets the endpoint choice. Completed trial
  results remain available. Unreviewed candidates and unfinished trials block selection.
  Source plans must use `/composition` for parameter edits and rendering; legacy edit
  fields cannot replace an already reviewed source snapshot.
- `{"candidate_id":"...","role":"decode","replicas":2}` creates a new, live-validated
  user revision. `role` is `decode` or `prefill`. Optional `tensor_parallel_size`
  and `replicas` are 1–128. Optional runtime edits are `max_model_len`
  (256–1048576), `gpu_memory_utilization` (0.5–0.98), `max_num_seqs` (1–4096)
  and `max_num_batched_tokens` (256–131072). Runtime edits affect all serving roles.
- `{"candidate_id":"...","native_cpu_cache_gib":4}` edits an already selected
  CPU KV cache, in GiB per model replica (greater than zero, at most 1024).
  The total must fit 25% of currently discovered free host memory.
- `{"candidate_id":"...","render_resources":true}` generates source-pinned YAML
  using the same renderer as Configuration and validates manifest consistency.
  It reads cluster/storage state and may fetch official sources, but does not
  install anything. Do not combine rendering with edits.

Edits preserve the original run, set `parent_run_id`, increment `revision`, and
invalidate old resource checks and performance evidence. Failed edits return
`409`. Rendering errors retain their status; a concurrently changed selection
is rejected. Successful rendering sets `validation.status=resources_checked`;
the manifest is in `configuration_plan.configuration.content.officialGuide.renderedManifest`.
The legacy renderer remains compatible with the original five mechanism IDs;
broader catalog constraints require `/composition`. Manual retains
distinct supported recipe/cache families and invokes
`{"candidate_id":"...","render_resources":true,"compare_combinations":true}`.
This Manual-only option checks retained recipes against pinned source without
publishing intermediate selections. It reports rejected candidates and selects
the greatest actual enabled capability coverage after source validation, breaking ties
by planning order. `validation.coverage` reports `enabled`,
`available_in_other_combinations` and whether coverage is `complete`.
Missing adapters are `unsupported`, not `conflict`; Agentic omissions can be `alternative`.
If none pass, `409` preserves the original
recommendation and blocks approval. Permission and unexpected server errors
propagate rather than being treated as recipe incompatibility.
Without `compare_combinations`, rendering preserves the explicit candidate choice.
Effective source-enabled prefix caching
and chunked prefill are recorded as enabled even when inherited from a Guide.
Manual enables supported runtime flags even when their workload benefit is unknown.
For direct vLLM sources that omit those flags, configuration includes a mandatory
startup CLI capability probe using the selected runtime image; a failed probe blocks
model startup. This does not certify runtime readiness or measured performance.
Required runtime flags and explicit exclusions must be verified before publishing
the checked configuration. Disabling engine prefix caching excludes dependent routing/offload candidates.
Prefix caching required by a sized CPU-cache recipe is recorded as `dependency`.
Topology revisions preserve the allocation per replica; explicit cache edits revise
it. Both recheck the 25% host-memory
budget; approval refreshes this budget again.
Admission, readiness and workload performance remain pending.

**`POST /api/agentic-deployments/{run_id}/approve`** returns `202`. New shared
plans must have reviewed/generated resources; otherwise it returns `409`.
Send `{"configuration_checksum":"<reviewed configuration checksum>"}`; a missing
or stale checksum also returns `409`. Concurrent approval or candidate mutation
is rejected while approval is in progress.
Capacity is refreshed before submitting the stored configuration to Deploy.
For DisaggregatedSet configurations the first approval returns `configuration_plan.validation.preparedDeployment`
without starting a deployment. Inspect its cases and preflight, then submit the same approval (including the
selected `endpoint` for source compositions) with `prepared_plan_id` set to its `id` and `expected_plan_digest`
set to its `digest`. Unknown preflight constraints require explicit `acknowledge_unknown: true`; failed checks block execution.
The execution response contains `deployment_run_id`. Generation is not a guarantee of
admission or readiness. Legacy approval remains compatible.

Shared plans reject the legacy `/refine` prompt-only operation with `409`:
create another plan with changed structured requirements instead.
Completed new runs/revisions are recoverable from snapshots through the existing
`GET /api/agentic-deployments/{run_id}` endpoint.

**`POST /api/v1/configurations/plan`** remains an intent-inspection compatibility
endpoint. It performs no cluster reads and returns no executable candidates,
no topology and no enabled mechanisms. Workload applicability remains unknown
until real planning; it no longer invents candidate rankings.

<TabItem value="python-api" label="Python API">

Source rendering is shared by both planning modes. `authorized_inventory(request,
selection)` returns the authorized source root and catalog; `render_unit(root,
catalog, unit)` previews a source component. `compose(request, body)` validates
and returns a bundle without persisting a deployment. `render_source_plan(service,
run_id, payload, request)` validates and persists the reviewed plan revision.
Pass an authenticated request context, never an invented principal.
`compose` applies the same capacity-domain constraints for automatic hard slice
placement and returns the eligible domains in `sliceLayout.recommended`.

```python
from llm_d_lens.agentic.service import service
from llm_d_lens.agentic.source_plan import SourcePlanRequest, render_source_plan
from llm_d_lens.deploy.source_catalog import authorized_inventory
from llm_d_lens.deploy.source_composition import render_unit, compose

async def preview_component(http_request, cluster_id: str, unit: dict):
```

### Commands and immutable artifacts

| --- | --- |
| `VersionedPayload` | Nonempty `schema_version`; object `value` defaults to `{}`. The envelope does not prescribe producer-owned keys. |

### RuntimeClass discovery and policy

`GET /api/v1/deployments/runtime-classes?cluster_id=CLUSTER_ID` requires deployment
read permission and access to the selected cluster. Optional `accelerator` and
`access_mode` identify a registered profile suggestion. The response includes
`items` (`name`, `handler`, `scheduling`, `overhead`, `matching_nodes`),
`profile_suggestion`, `available_suggestion`, `requirement="unknown"`,
`node_runtime_readiness="unknown"`, and `warnings`. Discovery or permission
failures at Kubernetes return HTTP 503, not an empty successful list. Unknown
hardware or access modes return HTTP 422; Lens authorization failures return 403.

Set `runtime_binding.runtime_class` on `POST /api/v1/deployments/runs`:

```json
{"runtime_binding": {"runtime_class": {"mode": "named", "name": "custom-runtime"}}}
```

The Python equivalent is `RuntimeBinding(runtime_class=RuntimeClassPolicy(...))`
from `llm_d_lens.deploy.contracts`. Standard and Agentic create requests expose
the same policy as top-level `runtime_class`.

- `auto`: preserve and validate an existing explicit manifest class; otherwise
  use the access mode's optional profile suggestion only when the target cluster
  advertises it. With no available suggestion, omit `runtimeClassName`.
- `node-default`: explicitly remove `runtimeClassName`. This opt-out does not
  require RuntimeClass discovery permission and does not verify device injection.
- `named`: require a DNS-subdomain `name` and validate its availability. Missing
  classes or conflicts with Pod node selectors/names fail before cluster writes.

Omitting the runtime override preserves a saved configuration's
`provenance.runtime_class`; without a saved preference the default is `auto`.
Explicit `auto` overrides a saved preference. Choices are retained in deployment
case policy for retry/restoration. The shared deployment adapter applies them
across all five model providers, deriving a new deployment artifact without
rewriting the supplied Configuration or existing executions. Router-only Pods
are unchanged. Offline rendering no longer injects unverified profile defaults.
The report is under `artifact.rendered_payload.value.deployment_contract.runtimeClass`.

Class existence and matching selectors do not prove that a class is required,
that its handler/CDI/drivers work on every eligible node, or that full scheduling
constraints can be satisfied. Device-plugin versus DRA access alone is not proof
either way. Select node default only when that cluster's default runtime already
provides device access. Automatic and named modes require a resolvable explicit
target cluster at deployment; offline provider rendering is not cluster validation.

### Execution, observation and evidence

Ordinary provider rendering maps `maxModelLen`, `maxNumSeqs`,
`gpuMemoryUtilization`, `blockSize` and `maxNumBatchedTokens` from each role
to the corresponding vLLM arguments. P/D uses separate `prefill` and `decode`
values; other providers use `decode` (`precise-prefix-cache-routing` also accepts
`serving`). `model.maxModelLen` supplies a fallback for missing role lengths.
Explicit integer controls must be positive integers; `gpuMemoryUtilization`
must be finite and greater than zero and at most one. Invalid values fail
validation/rendering instead of silently falling back. Applicable
`customParameters` override structured controls. Ordinary rendering replaces both
`--name=value` and `--name value` forms; omitted controls preserve Guide defaults.
Exact published `officialGuide` manifests remain on their existing validated
manifest path rather than being rewritten by ordinary provider parameter mapping.

`DeploymentExecution` carries `execution_id`, `request_id`, `status`, `artifact`,
`configuration_artifacts`, optional `endpoint`/`namespace`/`resource_snapshot`,
`provenance`, `evidence_refs`, optional versioned `diagnostics` and timestamps.
Additional current fields are `forwarded_endpoint`, `monitoring_setup` (setup
audit, not live monitoring status), `data_plane`, and editable descriptive
`metadata` (`display_name`, `description`), separate from origin provenance.

The complete run/case/execution state enums are listed below. A `ready` execution
must contain `DeploymentEndpoint`: `url`, `protocol="http"` and optional
`service_ref`, `model_ref`, `baseline_url`. Endpoint metadata must not carry
credentials, kubeconfig or authorization values.

Shared-memory preparation is recorded under
`artifact.rendered_payload.value.deployment_contract.sharedMemory` and copied to
`diagnostics.value.snapshot.shared_memory`. The report contains `defaultSizeLimit`
(`4Gi`), `addedMounts`, per-container `mounts`, `warnings`, and `manifestChecksum`
for the shared-memory preparation stage (before later placement or tracing).
Ordinary renders complete missing model-server `/dev/shm` mounts; existing mounts
and host IPC are retained. Published `officialGuide` manifests are checked without
shared-memory mutation. Warnings are also logged; invalid or duplicate mount
bindings fail rendering. This does not change the supplied Configuration artifact.

`get(execution_id)` returns `DeploymentExecution`, not another status DTO.
The concrete service looks up its in-memory execution state and raises `KeyError`
for unknown IDs; it is not itself a database query. The worker/DAO boundary owns
durable records and restores execution context when needed. The protocol also
exposes `restore_execution`, `refresh_diagnostics`, `stop` and `clean`; use the
authenticated REST operations below for external clients.

`get_logs(DeploymentLogRequest(...))` returns a `DeploymentLogPage`, separate from
execution metadata:

- Request: `execution_id`, optional nonnegative integer-string `cursor`,
  `limit` from 1 to 1000 (default 100), `follow=False`, and `sources=[]`.
- Current sources are `workload` and `events`, not arbitrary Kubernetes selectors.
  Entries contain `timestamp`, `source`, `message` and optional `severity`.
- Response: `execution_id`, `entries`, `next_cursor`, `complete`, `evidence_refs`.
  `follow=True` sets `complete=False`; this method still returns one page, not a
  streaming iterator or a promise to wait for new logs.
- Archived diagnostics use `ExecutionLogArchive` and
  `deployment-log://<execution_id>/archive` references. Preserve evidence separately
  from database records; see [storage settings](/environment-variables#storage-and-cache-paths).
  Retained snapshots are partial diagnostics, not a complete cluster log history.

## Backend API

### Deployment verification

| Method and path (under `/api/v1/deployments`) | Permission | Result |
| --- | --- | --- |
| `POST /executions/{execution_id}/verifications` | `deployment:execution:connect` | `202`, persisted queued check |
| `GET /executions/{execution_id}/verifications` | `deployment:run:read` | `{items: [...]}`, newest first, latest 20 |
| `GET /executions/{execution_id}/verifications/{verification_id}` | `deployment:run:read` | One saved record, `404` if absent |

All three enforce deployment resource scope. POST accepts `checks` (unique nonempty
subset of `chat`, `prefix_cache`;
default `["chat"]`) and strict integer `requests` (1–20, default 10). Prefix cache
requires at least 10 total requests and consumes six of that budget. Invalid bodies
return `422`; non-ready/model-less deployments or an active check return `409`.

Records include `id`, `execution_id`, `request`, `status`
(`queued|running|succeeded|failed`), timestamps, `requests_sent`,
`requests_completed`, `requests_succeeded`, `output_tokens`, `max_output_tokens`,
and, on completion, `verdict`, `evidence_sufficient` and `checks[].evidence`.
Attempted requests count before HTTP dispatch; completed counts HTTP responses,
not successful completions. No model response text or owner identity is exposed.
Task completion and evidence verdict are separate. KV/rank/routing checks are not
accepted for new tasks; older records remain readable. Zero or missing cache counters
stay inconclusive. Observed chat failures are not masked by other transport errors.
Each request times out after 10 seconds and there is no overall limit; tasks left
unfinished by a backend restart are marked failed at startup without replay. Reads
have no lifecycle side effects.
Records live in existing diagnostics JSON, survive stop/clean and disappear with
execution history. Active checks register as deployment consumers.

```python
from llm_d_lens.deploy.verification import start_verification, get_verification
from llm_d_lens.deploy.verification_checks import VerificationRequest

# Inside an authorized async request/task on the Lens host:
task = start_verification("execution-1", VerificationRequest(checks=["chat"], requests=2))
saved = get_verification("execution-1", task["id"])  # persisted-only read
```

Service functions assume the caller has performed resource authorization; the
public REST routes do so for both Web and MCP. No database migration is needed.

Stop, clean, restart and delete operations check Deploy's registered usage probes
before changing workloads or removing records. Active evaluation consumers and
published model-service members block these operations with HTTP `409` and code
`deployment_in_use`; unpublish members before teardown. Probe failures fail closed.
Run deletion checks every case before starting cleanup. Python worker callers
receive `deploy.usage.DeploymentInUseError` (a `ValueError`). These state checks
do not reserve the deployment atomically against a concurrently starting consumer.

Guide compatibility endpoints keep the `{ "error": "..." }` response shape.
Expected validation failures retain their actionable message and status.
Unexpected catalog/preparation failures return a generic `502` response; unexpected
planning failures return a generic `500` response with `Server-Timing` preserved.
Exception details are logged on the server, not returned to the browser.

```json
{"ready": true, "commit": "selected-source-commit", "capabilities": {"cacheCpuGiB": false, "rdmaNicCount": true}}
```

The booleans describe supported CPU-cache mutation and a matching profile NIC

Agentic create and refinement streams use `llm_d_lens.agentic.streaming.planning_stream_response`. The routes retain principal resolution, expected-error classification, and their existing generic error messages. Streams emit `progress` followed by `complete` or `error`; disconnect cleanup cancels and awaits unfinished planning. Gateway operation/log streams remain separate.

Recalculating an Agentic plan does not require an AI provider. Without one,
`AgenticDeploymentService.refine()` refreshes planning facts and uses deterministic
candidate generation and scoring with the new preference. If an available AI
scorer fails, recalculation keeps the validated candidates and returns
deterministically scored alternatives instead.

Refinement replaces the current plan only after evidence access is rechecked and
the new audit snapshot is saved. A failed refinement preserves the previous plan;
if the plan changes while recalculation or approval is in progress, reload it
before retrying. Selecting an alternative updates the decision's SLO status and
evidence to that candidate without rewriting the earlier audit snapshot.
Approval leaves `awaiting_approval` before submitting to Deploy, so the same plan
cannot be submitted twice. An interrupted or failed submission marks the Agentic
run `failed`; inspect deployment runs before creating a replacement plan.

Agentic candidate planning and approval revalidation use the deployment request's
`max_model_len` and `gpu_memory_utilization` for memory and KV-cache checks, even
when the supplied `planning_facts` contains different values. Deterministic and
AI-generated candidates use the same utilization as the deployed configuration.
PD deployments apply that utilization to both prefill and decode vLLM roles.
The estimate uses GPU capacity and model overhead, not vLLM's measured free KV
cache at startup.

### Multi-source evidence in Agentic plans

`AgenticDeploymentService.create()` and `.refine()` resolve evidence using the
actual request principal. REST and streaming calls retain that identity.
Public Prism observations use exact model/live hardware filters and require global
`benchmark-rag:query:read`; internal experiments retain their resource authorization.
Client-supplied public observations and cases are not trusted.
Plans containing public observations keep the same read-permission requirement.

Each `create()` or `refine()` call shares one request-local hardware discovery
snapshot between planning facts and public evidence retrieval. Later calls and
deployment approval discover resources afresh. Accelerator identity and usable
VRAM come only from live automatic discovery; test-only hardware and VRAM
environment overrides are no longer supported. Missing usable VRAM stops
planning rather than substituting a simulated capacity. Previously created
simulation plans remain blocked from deployment. Historical matching uses the
deployment runtime's serving backend. Public records with a missing, blank or
`unknown` backend default to `vllm` in SQL matching and returned experiment/case
context; explicit other backends are not reclassified. Stored records and original
source evidence are unchanged; unknown runtime versions remain unknown.
TPOT prompt targets accept `ms/token` and `s/token`, normalized to milliseconds.

Benchmark comparisons treat equivalent decimal workload values numerically,
recognize `latency`/`e2e` as end-to-end latency aliases and normalize fractional
percentiles such as `p99p9`/`p99.9`. Original source evidence is retained.

The server normalizes explicit workload and latency requirements, aggregates
experiments by configuration and series before limiting each SQL branch to 50
cases, then selects at most 10 complete cases within a 16,000-byte evidence budget.
Explicit workload fit precedes comparable lower latency; no workload means no
workload penalty. Missing measurements remain unknown. Different statistics and
experiments are not combined to manufacture an SLO result. Cases without comparable
workload or valid latency are explicitly labelled fallback references.
All requested latency metrics must be available with the requested statistics
before a candidate can receive an SLO conclusion. Missing metrics remain
`unknown`, not satisfied or failed. TTFT/TPOT evidence alone cannot establish
an end-to-end latency target, so such a plan retains `unknown` SLO status.

`planning_evidence` keeps public retrieval under `id="public-rag:query"`, including
available, no-match, forbidden and unavailable outcomes. Configuration-case details
retain source conditions, differences, unknowns, branch status and truncation.
Candidate explanations and server-side audit retain their evidence boundaries:
historical measurements are not proof of current performance, and AIC is an estimate.

Planning uses public and internal SQL experiments, without a document retrieval
branch, embedding/vector search or document packet contracts. Model prompts name
these sources published benchmark evidence and internal benchmark history and
instruct decision explanations to use those terms. Standalone public observations use the model-context key
`published_benchmark_evidence`; an empty context means no evidence was supplied for
that request, not that the databases contain no data.
The stored `public_rag_evidence` field, `public-rag:query` evidence ID and
`benchmark-rag:query:read` permission remain legacy compatibility identifiers, not
claims of document retrieval capability. The existing private diagnostic adapter
is unaffected.

Creation validates the registered model-cache storage volume without requiring
downloaded model files. Refinement likewise skips download-readiness checks.
Approval requires a ready cached model, resolves its current credential policy,
refreshes resource validation and requires explicit user approval.

Deployments live under the FastAPI router in `llm_d_lens/deploy/router.py` with the `/api/v1/deployments` prefix.

Use the [installation instructions](/installation) and
[storage environment settings](/environment-variables) for the current monorepo
and Lens storage roots. The old `.llm-d-bench/deploy` and host-specific
`/root/.llm_d_lens/run_store` paths are not the current storage contract.

Execution discovery is read-only and uses `execution_id` as its cross-module
reference; listing does not start port-forwards. Use the execution endpoint
action to obtain a host-reachable URL rather than assuming a persisted
in-cluster endpoint or old tunnel is reachable.

Execution list/detail REST responses additionally expose `run_id`, `case_id`,
`ownership` (`self`, `other`, `unknown`) and `capabilities` (`update`, `stop`, `delete`).
Capabilities are calculated for the authenticated caller using the same RBAC checks
as writes; they are advisory and writes reauthorize. Owner user/group ids are not
returned. Detail includes `configuration`, the exact source `DeployableConfiguration`
selected by that case's `source_configuration_ordinal`, when the source run exists.
It is the saved configuration, not a reconstruction of live manual scaling.
The Python `ExecutionContext.api_payload()` remains a neutral runtime projection;
the REST router adds caller-specific fields.

| Record | Lifecycle states |
| --- | --- |
| Run | `queued`, `running`, `succeeded`, `partially_succeeded`, `failed`, `cleaned`, `cancelling`, `cancelled` |
| Case | `queued`, `rendering`, `deploying`, `ready`, `failed`, `stopped`, `cancelling`, `cancelled`, `cleaned`, `cleaned_up` |
| Execution | `draft`, `validated`, `rendered`, `deploying`, `ready`, `failed`, `rolling_back`, `rolled_back`, `cleaned`, `cleaned_up` |

A stopped case has a `rolled_back` execution; these are different state enums.
Benchmarking requires a ready execution with an endpoint and an active cluster
session. Python worker examples below run inside a configured Lens backend;
external clients should use authenticated HTTP so route permissions and resource
scope checks apply.

Optimized and precise routing capability metadata reuse `shared_prefix_routing_workload()` in `llm_d_lens.deploy.capabilities`. Each scenario and recommended workload receives independent nested values; provider-specific baselines and goals are unchanged. Precise-provider calibration and model discovery share lazy modelserver invocation traversal while retaining their respective last-value and first-model selection rules.

Agentic candidate generation requires its first tool batch to contain exactly
`get_cluster_overview` and `search_candidates`. An invalid first batch is not executed;
the generator gives the AI one corrective retry before using built-in candidates. If
the retry also violates the tool contract, the fallback is reported as an invalid
generator response rather than a provider connectivity failure. A tool-call limit
failure retains the round, observed call count, and limit in
`generator_fallback_detail` on the run and `generator.fallback_detail` in its
planning snapshot; `generator_fallback_reason` remains the stable category.

Agentic generator and planner user messages begin with the operator's full preference,
before the JSON context. Their instructions prioritize platform/hardware validity,
explicit user requirements, soft preferences, then evidence and diversity. Diversity
must not introduce forbidden topologies; selection may return fewer than three options.
This is prompt guidance, not a general server-side natural-language constraint parser.

Planning snapshots (schema version 2) preserve `request.planner_prompt` without redaction.
`planner_prompt_present` remains a compatibility indicator, not a substitute for the text.
Run fields `generator_requests` and `planner_requests` contain the actual provider-native
request bodies, raw responses, timestamps, HTTP status, and error type for every HTTP attempt,
including retries. Snapshots expose these under `generator.requests` and `planner.requests`.
Stage audit files under `session-artifacts/agentic-planning/<run_id>/requests/` are persisted
before sending and after completion, including failed or cancelled planning with no final
run. Authentication headers and API keys are excluded; full prompts and tool context are
private application data. Auditing applies to new requests, not historical reconstruction.

Agentic candidate submissions accept `optimized-baseline`, `pd-disaggregation`,
`tiered-prefix-cache`, and `precise-prefix-cache-routing`; `baseline-vllm` is rejected
by the generator schema and excluded from planner ranking. Aggregated AIC recommendations
map to `optimized-baseline`, including load-target and relaxed-anchor paths.

Agentic planning estimates missing exact AIC predictions separately for each validated
optimized-baseline and pd-disaggregation candidate using its workload and GPU topology. The
candidate's estimate is supplied to AI scoring as `aic_estimate`; an unavailable estimate remains
unknown, not a performance or SLO guarantee. Agentic estimates do not pass the original search
TTFT/TPOT targets; they verify the fixed topology and workload without an SLO filter. Generator
fallback also estimates the top three built-in candidates, using the resolved workload when the
failed generator left no tool trace. Unsupported or unavailable topologies remain unknown. Relaxed AIC
search accepts complete configurations using no more than the available GPU budget. Its predictions
do not establish compliance with the original SLO. Agentic preserves the relaxed anchor as a
validated candidate even when the generator suggests only a smaller topology, then estimates its
exact topology and workload. Candidates with known estimates that miss the original latency targets
are marked `not_satisfied`; among comparable misses, smaller relative target violations rank ahead
of GPU savings. Unknown estimates are not treated as failures.
When an external planner scores multiple candidates, its selection rationale explains why each
lower-scored returned candidate ranks below the top choice using the supplied planning facts. Only
the returned top three are scored; no reason is inferred for candidates outside that set.

Planning-fact collection matches discovered accelerator models against registered hardware profiles
to select one AIC system. Unknown, ambiguous, or mixed systems leave AIC evidence unavailable.

AISimulate support checks and estimates use the release pinned in
`pyproject.toml` (currently 0.13.0), including its bundled support matrix and
performance data. The existing `/api/v1/aic` routes and request fields remain
for compatibility. An unsupported P/D result describes the installed matrix,
not a hardware-level prohibition; candidate availability also depends on the
requested workload and GPU budget. After changing the dependency pin, reinstall
project dependencies and restart the backend so support checks and searches use
the same SDK release.

### Search or size an AISimulate workload

The MCP generation and plain-estimate fallback behavior above applies when no load
target is supplied. Agentic load-target planning instead validates the exact
AISimulate recommendations, including replica counts outside the ordinary candidate grid.

    **`POST /api/v1/aic/search`**

    `mean_input_tokens` defaults to `4000` and `mean_output_tokens` to `1000`, matching
    the AISimulate compatibility API's search/recommend defaults. Supply either positive `target_concurrency` or

    input. Lens scales the recommended worker pools and accepts only configurations

#### Shared estimate contracts (development)

The separate shared Python contract in `llm_d_lens.estimate_tools.models`
accepts an optional `Configuration.offload` block, for example
`{"tiers": [{"tier": "cpu_dram", "bytes": 1073741824}]}`. The current
implementation represents one CPU KV tier with `OffloadingConnector`, either
`CPUOffloadingSpec` or `TieringOffloadingSpec`, and LRU eviction. The managed
BLIS profile must explicitly approve CPU offloading; requests cannot enable
that server-owned permission. NVMe tiers, LMCache connectors and connector
options are not represented. Disabled offloading preserves existing configuration
fingerprints; enabled tier capacity is part of the identity.

AISimulate explicitly refuses this block instead of ignoring it. These are not
new fields on the legacy `AICEstimateRequest` or `/api/v1/aic/*` routes. Internal
BLIS topology, capacity and joint TTFT/TPOT grid searches remain private Python
development interfaces, without HTTP, MCP, Configuration UI or Agentic dispatch.
Joint search also accepts an end-to-end `latency_target_ms`. At least one latency
target is required; each selected statistic defaults to p99 and missing native
evidence stays unknown. Omitted topology axes generate a bounded family from the
available GPU budget and fixed PP/DP: powers of two, device-budget boundaries and
whole-node TP groups. Explicit topology grids override generation. Configuration
recommendation requires one explicit business load in `workload.request_rate` or
`workload.concurrency`, preserved for every candidate. Load grids and implicit
load generation are not accepted by recommendation. The default `mode="economic"`
ranks target-satisfying configurations by fewer used devices, then greater measured
throughput. `mode="performance"` prioritizes measured request throughput within
the device budget, breaking throughput ties by lower latency (TTFT, TPOT, then
end-to-end latency at the selected statistics), then fewer devices. At fixed QPS,
fully served candidates may have similar throughput; this is not a capacity claim.
The independent capacity sweep preserves a fixed configuration and evaluates an
explicit QPS or concurrency grid, reporting feasible tested loads without ranking
or recommending configurations.
Recommendations include device counts and native metrics. These are best observed
points, not global optima or promises to serve an unspecified load. Missing run
controls inherit the managed profile's verified controls, not invented evidence.
Only fully completed, constraint-satisfied observed points can be recommended;
simulator results do not establish prediction accuracy or deployment approval.

Private sweep results separate `execution_counts` from `constraint_counts`; the
latter counts successful evaluations only. Grid exhaustion is not a feasibility
proof, and finite request completion does not certify sustained business load.
Each executed point retains `execution` metadata and at most the last 4096 bytes
of native stderr, decoded with replacement for invalid UTF-8. The
`stderr_tail_truncated` flag reports tail truncation separately from the execution
output limit. Diagnostics survive temporary bundle cleanup and do not affect point
identity. Topology search exposes failed execution metadata by configuration
fingerprint in `execution_diagnostics`. Native stderr is diagnostic text, not a
typed capacity verdict: unknown process failures remain failed/unknown, never
silently classified as infeasible from memory-related wording.

### Start a standard vLLM deployment run

Start a Standard Kubernetes Service deployment run using Lens's allowlisted vLLM contract.
The generated namespace uses the backend's configured deployment prefix (for example, `llmd-baseline-vllm-...`).
Standard vLLM deployments use the baseline adapter for rollout readiness and cleanup; they do not require a published Guide manifest's `readinessDeployments` contract.
Only registered Model Cache storage is accepted. It requires a ready entry for the selected model and serves it offline using the entry's downloaded revision; a conflicting custom vLLM `revision` is rejected. Requests using `local-cache` or direct `pvc` storage fail validation. Shared creation preflight also revalidates model/revision readiness and local-disk node synchronization through `llm_d_lens.deploy.providers.storage_mount.require_cached_model`. Ordinary provider rendering mounts the registered cache read-only for serving; `cacheOffline=false` cannot disable its offline flags. Exact published manifests are not covered by those rendering guarantees. Missing or incomplete models must be downloaded or synchronized through Model Cache.
The generated run defaults to preferring replicas on one node without making it mandatory. `placement_replicas` also supports required co-location, balanced distribution, or required separation across model-server Pods in the same rendered manifest. For required co-location, `placement_node_label` can restrict the Pods to a selected cluster node by its `kubernetes.io/hostname` label; the label is checked against that cluster before deployment. Tensor-parallel accelerator claims are requested by each model-server Pod, keeping its TP devices in that Pod. Agentic planning inherits the same fields and applies the selected preset on approval.

### List deployment executions

from the stored rendered vLLM manifest. Flat runtime parameters describe the decode

### Delete a deployment run

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`DELETE /api/v1/deployments/runs/{run_id}`**

No request body. Requires `deployment:execution:delete` and access to the run.
Returns `204` with no body. Missing runs return `404`; active
(`queued`, `running`, `cancelling`) runs or lifecycle conflicts return `409`.
Cancel active orchestration and wait for a terminal state before deleting.

This is not a metadata-only delete: remaining cases with stored executions are
cleaned first, requiring their active cluster session, then stored run/execution
records and associated shares are removed. Already-cleaned cases are skipped.
By contrast, case `clean` removes runtime resources but retains the lifecycle
record; `preserve_rendered_overlay=true` retains rendered files.

Example request: `DELETE /api/v1/deployments/runs/run-1` (no JSON body or response).

### Refresh a deployment case

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`POST /api/v1/deployments/runs/{run_id}/cases/{case_id}/refresh`**

No body is required (`{}` is accepted). Requires `deployment:case:execute`.
Returns `200` with the same `case`, `execution`, and `deployment` envelope as
Get case, refreshed from provider diagnostics. Stopped or cleaned records are
preserved rather than made ready again. Missing case/execution or refresh
`ValueError` returns `404`. Response excerpt:

Progress-deadline errors remain `deploying` while current Pod diagnostics confirm
normal container startup within probe budgets, counted from container start
rather than time spent Pending. A recoverable `failed` record returns to
`deploying`; the case failure is cleared. `diagnostics.value.snapshot.pod_statuses`
contains Pod status and probe timing fields, not container environment values.
Running alone does not set `ready`, and current workload failures or expired
startup budgets are not treated as normal startup.

```json
{
  "case": {"id": "case-1", "status": "ready", "execution_id": "execution-1"},
  "execution": {"execution_id": "execution-1", "status": "ready"},
  "deployment": {"run_id": "run-1", "case_id": "case-1", "status": "ready"}
}
```

### Restart a deployment case

:::warning Current restart limitation

The route exists, but the current worker cleans the old execution and marks its
case `cleaned` before calling `DeploymentPlanService.retry_case()`, which accepts
only the latest `stopped` or `failed` case. Consequently, successful cleanup is
followed by `409`, not a queued replacement. Cleanup has already taken effect;
an error is not evidence that the old resources remain. Do not repeatedly retry
this route expecting it to restore the deployment.

:::

<Tabs>
  <TabItem value="rest-api" label="REST API">

**`POST /api/v1/deployments/runs/{run_id}/cases/{case_id}/restart`**

Requires `deployment:case:execute`, an active cluster session, and a stopped or
failed case. Body: `RestartCaseRequest`; `model_token` is an optional string
override, with empty/whitespace treated as absent. Send `{}` to omit it.
The declared success shape is HTTP `200`, `{ "case": ... }`, but the current
cleanup/retry conflict prevents that path after successful cleanup.
Lifecycle `ValueError` becomes `409`; invalid bodies return `422`.

```json
{}
```

Current conflict response excerpt (the application adds Problem Details fields):

```json
{
  "status": 409,
  "detail": "only the latest stopped or failed deployment case may be retried"
}
```

  </TabItem>
  <TabItem value="python-api" label="Python API">

```python

    try:
        case = await deployment_run_manager.worker_for_run("run-1").restart_case(
            "run-1", "case-1", model_token=None
        )
    except ValueError as error:
        print(f"Restart failed; inspect the case because cleanup may have occurred: {error}")
        raise
```

## Remote SSH deployment

SSH transport and remote command failures return `502` with
`{ "error": "Remote deployment failed" }`; internal exception details and failing
command output are logged server-side rather than exposed in error responses.
Expected input and policy errors retain their existing status and actionable message.

These legacy endpoints are implemented in the Python module
`llm_d_lens.deploy.remote_deploy`. They
execute commands over SSH rather than create v1 deployment runs. Their current
single-node Intel Data Center GPU/XPU restriction is specific to this legacy
implementation, not the capability limit of the profile-driven v1 API.

SSH operations require `PRISM_REMOTE_DEPLOY_ENABLED=true` in production (enabled
by default outside production). Production targets must also match
`PRISM_REMOTE_HOST_ALLOWLIST`. Defaults remain readable when SSH operations are
disabled, subject to authentication/permission checks.

| Operation | Lens permission |
| --- | --- |
| Defaults | `remote-deploy:target:read` |
| Fingerprint, test | `remote-deploy:target:connect` |
| Start, status, logs | `remote-deploy:deploy:execute` |
| Teardown | `remote-deploy:deploy:teardown` |

Authenticated SSH operations require `target.host`, `username`,
`hostFingerprint` and a nonempty `cards` array of numeric ID strings.
`port` defaults to 22; `authMethod` defaults to `agent` and also accepts `key`
or `password`. Agent authentication requires the BFF's `SSH_AUTH_SOCK`.
Key authentication requires a server-side `keyPath` beneath `PRISM_SSH_KEY_DIR`
(default `$HOME/.ssh`). Password authentication supplies
`credentials.password` on each request; it is not stored or returned.
Fingerprint discovery does not authenticate and does not require cards.
Confirm its result through a trusted channel before using it; a returned
fingerprint is not itself proof of host identity.

Route errors are `{ "error": "..." }`: `400` for invalid input/credentials,
`403` for a production host outside the allowlist, `503` for disabled SSH
operations, and normally `502` for SSH/command failures. Gateway authentication
and permission errors use the gateway's Problem Details format.

### Python HTTP client for remote operations

There is **no Python service-layer equivalent** for these Node endpoints.
The Python tabs below use this HTTP helper instead. The environment variables
in this example are client inputs, not new Lens server configuration.
Set them from an authenticated Lens session; never commit their values.

```python
import os
import httpx

def remote_request(method: str, path: str, body: dict | None = None) -> dict:
    with httpx.Client(
        base_url=os.environ["LENS_URL"],
        cookies={
            "prism_session": os.environ["LENS_SESSION"],
            "prism_csrf": os.environ["LENS_CSRF"],
        },
        headers={"x-prism-csrf": os.environ["LENS_CSRF"]},
        timeout=300,
    ) as client:
        response = client.request(method, path, json=body)
        response.raise_for_status()
        return response.json()

target = {
    "host": "192.0.2.20",
    "port": 22,
    "username": "operator",
    "authMethod": "agent",
    "hostFingerprint": os.environ["VERIFIED_SSH_FINGERPRINT"],
    "cards": ["0"],
}
```

REST request examples below show operation fields; for authenticated operations,
add the complete `target` object above and optional per-request `credentials`.
The Python examples demonstrate the complete request assembly.

## Configuration preparation APIs

These Configuration-domain routes prepare artifacts for Deployments and Evaluation. Request and response models live in `llm_d_lens.configuration.models`. The examples use illustrative cluster/session IDs and guide commits; replace them with an active cluster session and real rendered guide provenance. Saving publishes an artifact; rendering alone does not deploy it.

The workflow is source selection/editing, resolve, render, save, then deployment.
Resolve normalizes each source configuration before capability checking and
validation, returning per-configuration feedback. The candidate source identifies
input origin, not deployment type. Render binds candidate intent to actual Guide
resources; save publishes immutable artifact content, identity and checksums.
Configuration owns normalization, validation and artifact publication; Deploy
owns runtime validation, resource lifecycle, teardown and rollback. Checksums
alone cannot validate topology or resource semantics. These boundaries apply to
both the REST endpoints and their Python service functions below.

The HTTP boundary uses `application/problem+json` errors. Shared `DomainError` instances retain their original status and code (for example a conflict remains 409); they are not converted into an operation-specific 500. Python service calls raise their original exceptions; the route adapters in `llm_d_lens.configuration.router` apply the HTTP mappings below.

### Deployment access APIs (removed)

Deployment sharing and `deployment:run:share` have been retired. Use
[model-service inference grants](/api-reference/modules/model-services#model-inference-grants)
instead. Migration audits and removes existing deployment shares; it does not
convert them into broader model grants.

<Tabs>
  <TabItem value="rest-api" label="REST API">

The former GET/POST/DELETE `/api/v1/deployments/executions/{execution_id}/access`
and `/api/v1/deployments/runs/{run_id}/access` routes, including
`/access/options` and `/access/{binding_id}`, are no longer registered.
They no longer grant, list or revoke access.
  </TabItem>
  <TabItem value="python-api" label="Python API">

Replace deployment-share calls with the model service's scoped grant methods:

```python
from llm_d_lens.model_service.service import default_service

def revoke_model_grant(model_id: str, binding_id: str, principal) -> None:
    default_service().revoke_access(model_id, binding_id, principal=principal)
```

The method requires `model-service:group:share` in the model's cluster and rejects
bindings belonging to another model. Generic binding creation rejects retired
`deployment_run` and `deployment_execution` resource types.

## Measured Agentic optimization

`POST /api/agentic-deployments/{run_id}/optimize` returns HTTP 202 and the updated
plan. It requires Agentic approval and benchmark creation permissions, cluster
access and an active session. `POST /api/agentic-deployments/{run_id}/optimize/cancel`
stops the task and cleans up its test deployments. Read progress through the
existing `GET /api/agentic-deployments/{run_id}` response's `optimization` field.

```json
{"candidate_ids":["candidate-a","candidate-b"],"objective":"throughput","max_gpu_count":8,"max_duration_minutes":60,"max_benchmark_runs":5,"repetitions":2,"confirmation_runs":1,"max_error_rate":0,"benchmark":{"matrix":[{"isl":512,"osl":128}],"concurrency_stages":[{"concurrency":4,"num_requests":100}]}}
```

The Python request type is `llm_d_lens.agentic.optimization.OptimizationRequest`.
Objectives are `throughput`, `latency` and `throughput_per_gpu`. Optional
`native_cpu_cache_gib` adds composition variants; its repetitions also count
against `max_benchmark_runs`. Budgets are 1–1024 GPUs, 1–180 minutes, 1–30 runs
and 1–3 repetitions. Invalid or insufficient budgets return 422 before starting.
The response records `samples`, `ranking`, `best_candidate_id`, status and scope.
Only completed comparable samples satisfying configured SLOs and the error cap
are ranked. Cleanup failures remain visible and block approval.

Matrix and shared-prefix trials require every requested stage. Each repetition
uses the highest measured stage P95 latency and error fraction, and the lowest
stage token throughput. These are conservative stage bounds, not a pooled P95
or an average across different workloads. Missing metrics remain unknown.

`confirmation_runs` is 1-3 (default 1). After comparisons, the leading candidate is
deployed again and measured with the same workload. `max_benchmark_runs` defaults
to 5 and must cover all comparison repetitions plus confirmation. The response
records these independent samples under `optimization.confirmation`, including
`candidate_id`, `status` and `samples`. `best_candidate_id` remains null unless
confirmation meets the SLOs and error limit and cleanup succeeds. Comparison
rankings are retained even when confirmation fails; they do not establish a
confirmed winner. External AI is optional and never substitutes for measurements.

```python
from llm_d_lens.agentic.optimization import OptimizationRequest

request = OptimizationRequest(
  candidate_ids=["candidate-a", "candidate-b"],
  max_gpu_count=2,
  max_benchmark_runs=5,
  repetitions=2,
  confirmation_runs=1,
  benchmark={"matrix": [{"isl": 512, "osl": 128}]},
)
payload = request.model_dump(mode="json")
```

For interrupted cleanup, the cancel endpoint accepts the optional `cluster_session_id` query parameter. It must resolve to the original test cluster; a different cluster is rejected with HTTP 409.

`guideComposition.nativeCpuCacheGiB` also supports `pd-disaggregation` with built-in NixlConnector/kv_both on both roles. The adapter emits ordered MultiConnector children and an image-matched capability init container; saved manifests must retain both. `native_cpu_cache_gib` in measured optimization adds P/D variants as well. Missing adapters, mismatched images, missing roles, and modified cache budgets fail validation. Capability checks do not replace workload correctness tests or benchmarks.
